# PR 本文

根拠を判断に必要な場所へ置き、PR 本文だけで変更の判断と検証を再構成できるようにする。

## 根拠を置く場所

| 場所 | 書く内容 |
| --- | --- |
| コード内コメント | コードと同じ寿命を持つ実装意図 |
| 行指定コメント | その行でしか意味を持たない根拠 |
| PR 本文 | 背景、変更の構造と判断、影響、検証、レビュー観点 |
| コミットメッセージ | そのコミットをその順序で入れる理由 |
| `docs/DESIGN.md` | 恒久的な設計判断、不変条件、却下した案 |
| `docs/ISSUES.md` | コードから確認したスコープ外の不具合 |

同じ根拠を複数の場所に書かない。
`docs/DESIGN.md` がある場合は恒久的な判断をそこへ書き、`変更内容` には要点と該当見出しへのリンクを置く。
関係する `docs/ISSUES.md` の項目や外部 Issue は、本文から識別子または URL で指す。

## 章立て

最初の 6 章を次の順序で必ず置く。
`関連` は該当項目がある場合だけ末尾に置く。

```markdown
## 背景

[必要な経緯、目的、目的としないこと、未対応事項を書く。]

## 概要

[採用した手段を 1 文から 3 文で書く。]

## 変更内容

[変更と技術判断の理由を関心事ごとに書く。必要なら h3 を使う。]

## 影響範囲

[影響を受ける利用者、契約、運用を書く。]

## 検証

- [x] `[実行したコマンド]`：結果
- [ ] 未検証：[対象と理由または残作業]

## レビュー観点

- [確認してほしい場所と判断内容]

## 関連

- [依存 PR または Issue と、この PR との関係]
```

## 各章を書く

- `背景`：リンクを開かなくても必要性が分かるようにし、目的としないことや未対応事項も判断に必要なら書く。
- `概要`：背景を繰り返さず、採用した手段だけを 1 文から 3 文で書く。
- `変更内容`：機能、責務、データフローなどの関心事ごとに理由を書く。重要な却下案は理由とともに書き、複数の関心事を分ける必要がある場合だけ h3 を使う。ファイル一覧にはしない。
- `影響範囲`：利用者、後方互換性、API、設定、保存形式、CLI 引数、運用への影響を書く。影響なしとする場合も確認範囲と根拠を書く。
- `検証`：実施済みは `- [x]` とコマンドまたは再現手順と結果、未検証は `- [ ]` と対象および理由または残作業を書く。自動テスト、手動確認、測定結果をこの章に置き、手動確認は再現できる手順にする。確認していないことを保証しない。
- `レビュー観点`：場所と判断内容を具体化し、3 件までにする。4 件以上なら PR の分割を再検討する。
- `関連`：依存 PR、依存される PR、Issue の番号または URL と、依存方向または関係する理由を書く。該当しなければ見出しを置かない。

外部ドキュメントを根拠にする場合は、該当箇所へ直接届く URL と必要な短い引用を添える。
CI の失敗を根拠にする場合は、ジョブの URL と失敗を示すログを添える。
推測は推測と明示し、確かめなかった理由を書く。
指示や仕様にない判断を補った場合は、その箇所と根拠を明示する。

## 書かないこと

- ファイルごとに差分を転記した一覧
- GitHub の差分で読めるコードの貼り付け
- 測定条件を満たさない性能や使用量の主張
- コマンド、結果、理由がないチェックボックス
- 謝辞、自己弁護、レビュー判断に不要な経緯
