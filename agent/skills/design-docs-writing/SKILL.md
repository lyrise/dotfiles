# 設計文書の記述規範

`docs/DESIGN.md` と `docs/ISSUES.md` を書くとき、直すとき、点検するときは、以下の規範に従う。

この規範が守ろうとしているのは 2 点である。
第一に、実装が進んでも文書の書き換え箇所が局所に留まること。
第二に、後から読む人（数か月後の本人、または AI エージェント）が、事実と推測と未決を取り違えないこと。

## 2 つの文書の責務

| 文書 | 受け持つもの |
| --- | --- |
| `docs/DESIGN.md` | なぜその形なのか。不変条件、採用理由、却下した案、未決の論点 |
| `docs/ISSUES.md` | コードを読んで確認した明確な不具合。起票までの作業用リスト |

境界は「直し方が分かっているか」で判定する。
何をどう直すか分かっているものは不具合であり `ISSUES.md` に書く。
何を選ぶかがまだ決まっていないものは設計論点であり `DESIGN.md` の設計判断章に書く。

不具合の一覧を `DESIGN.md` の一節として持たない。
件数が少なくても `ISSUES.md` に分離する。
両者は寿命が違い、`ISSUES.md` の項目は修正とともに消えるが、設計判断は残るためである。

## 3 つのモード

**新規作成**：コードを読み、`DESIGN.md` の骨格（§「DESIGN.md の章立て」）を先に立て、各章を埋める。
確認できなかったことは埋めない。
§「根拠の出所を区別する」に従って扱う。

**更新**：設計判断が変わったときにだけ本文を触る。
実装が進んだだけのときは、本文を書き換えず、現状と残作業章と `ISSUES.md` だけを直す。

**点検**：§「執筆後の点検」のチェックリストを機械的に走らせる。

## DESIGN.md の章立て

先頭 4 章と末尾 2 章は、この順序で必須である。
中間の各論章はプロジェクトによって変わる。

```
1. このドキュメントについて
   1.1 文書間の責務分担
   1.2 本書の時制について
2. 〇〇とは / スコープ外
   2.1 スコープ外
3. 全体構成
   3.1 コンポーネントとディレクトリ対応表
   3.2 処理の流れ
4. 中心概念

--- 各論（プロジェクト依存、章数も見出しも自由） ---
5. …
N. …

--- 末尾 ---
N+1. 設計判断
   N+1.1 決定済み
   N+1.2 保留
N+2. 現状と残作業
```

見出しには `## 1.` `### 1.1` の形で番号を振る。
`####` には番号を振らない。

用語の定義は第 4 章に置き、末尾の用語集にしない。
各論を読む前に語彙が揃っていなければ、各論が読めないためである。

### 1. このドキュメントについて

何を扱う文書か、想定読者は誰かを 2 文から 3 文で述べる。

**1.1 文書間の責務分担**は表で書く。
この節は必須である。
このリポジトリで何がどの文書の正なのかを列挙する（`DESIGN.md`、API 定義ファイル、`README.md` など）。
そのうえで、本書に置かないものを明示する。

**1.2 本書の時制について**では、本文が完成形を現在形で書かれていることと、実装状況は現状と残作業章にあることを述べる。
「いま何が動くのかを知りたい場合は N 章を先に読む」の 1 行を必ず置く。

### 2. 〇〇とは / スコープ外

何をするものか、想定する運用（規模、利用者数、公開範囲）を述べる。

**2.1 スコープ外**には、作らないと決めたものを列挙する。
そのうえで、それを外したことで持たずに済んでいる機構を書く。
「共有リンクを作らないので権限モデルを持たない」のように、スコープ外の決定と設計の単純さを結び付ける。
この一文があると、後からスコープを広げる提案の代償が読める。

### 3. 全体構成

**3.1** はディレクトリとコンポーネントの対応表にする。
各行に、パス、パッケージ名、役割を書く。
自動生成物には「手で編集しない」と表中に明記する。

**3.2** は処理の流れの図（§「図」）を置く。

### 4. 中心概念

本文とコードで一貫して使う語を定義する。
1 語につき `###` 見出しを 1 つ立て、次の順で書く。

1. その語が指すもの
2. コード上の型名と、API など外部表現での名前の対応
3. 隣接する語との違い（何がその語に含まれ、何が含まれないか）

型名が層によって変わる語は、必ず対応を書く。
名前が 2 つある事実自体が、層の境界を示している。

### 各論章

1 章に 1 つの関心事を置く。
層、機能、規約のいずれかである。

各節では、何をするかの前に、なぜその形かを書く。
形だけを書いた節はコードの重複であり、価値がない。

不変条件は、それが成り立つ前提とともに書く。
前提が崩れる条件まで書く。
たとえば「rename でアトミックに公開する」と書くなら、同一ファイルシステム内でしか成り立たないことと、別ファイルシステムだとどう壊れるかを続けて書く。

### 設計判断章

**決定済み**は `####` 見出しで 1 決定ずつ、次の型で書く。

```markdown
#### 決定の要約を体言止めか終止形で

**決定**
何を決めたか。実装ではなく約束を書く。

**理由**
なぜそれを選んだか。何を優先し、何を諦めたか。

**却下案**
検討して退けた案と、退けた理由。
```

**却下案**は、検討した案があるときだけ書く。
なかった決定には節を置かない。
ただし、コードや依存関係に一度採用した痕跡が残っている案は必ず書く。
書いておかないと、後から同じ案が再提案される。

**保留**は `####` 見出しで 1 項目ずつ、次の型で書く。

```markdown
#### 保留している論点

**現状**
いまどうなっているか。

**なぜ今決めないか**
決めずに済んでいる理由。

**決める条件**
何が起きたら決めるか。
```

**決める条件**は必須である。
これがない項目は保留ではなく放置であり、書く意味がない。
条件は観測可能な事象で書く（「LAN 外からのアクセスを実際に必要としたとき」「検索が実運用のツリーサイズで使い物にならなくなったとき」）。

選択肢が複数ある保留では、選択肢を番号付きで列挙し、それぞれの代償を 1 文添える。

### 現状と残作業章

実装状況をこの章にだけ書く。
本文の各節に状態の注記を散らさない。
先頭に実装状況のサマリ表も置かない。
状態を 2 箇所以上に書くと、必ず片方が腐る。

**ロードマップ**は表で書く。
順序は暫定であると明記し、守る必要があるのは依存関係だけであると述べる。
表の列は、番号、内容、前提とする依存の 3 つを基本とする。

不具合は書かない。
章の末尾に `ISSUES.md` への導線を 1 行置く。

### DESIGN.md に書かないこと

**他に唯一の正があるものを複写しない。**
API のパスやステータスコードの網羅的な一覧は API 定義ファイルが持つ。
バイト列のレイアウト、シリアライズのフィールド番号、エンコーディングの詳細はコードが持つ。
セットアップ手順と依存パッケージは `README.md` が持つ。

**機械的に引けるものを書かない。**
未実装箇所の一覧、`TODO` の一覧、ファイル一覧は書かない。
代わりに引き方を 1 行書く（「未実装箇所の現物は `rg 'todo!' src` で引ける」）。

例外は、表の形でしか全体を把握できない横断的な規約に限る。
「どの操作が同期でどれが非同期か」「エラー種別と HTTP ステータスの対応」のように、判断基準として一望する必要があるものは、複写ではなく規約の提示として書いてよい。
その場合、個々の定義は元の文書を見ることを明記する。

## ISSUES.md

### 全体の形

冒頭に次を置く。

1. この文書が扱うもの（確認した明確な不具合のみ）と、扱わないもの（設計論点は `DESIGN.md` の該当章）
2. 使い方（起票したら Issue 番号を追記、修正されたら項目ごと削除、行番号はずれるので修正時に再確認）
3. 調査日と対象コミット

調査日と対象コミットは必須である。
この文書はスナップショットであり、いつ時点の情報かが分からないと使えない。

続いて一覧表を置く。
列は ID、概要、深刻度、Issue の 4 つ。
ID は項目へのアンカーリンクにする。

表の下に、項目間の関係を 1 段落で書く。
同じ経路にある項目、まとめて直すのが効率的な項目を指摘する。

末尾に「ここに含めていないもの」の表を置き、`DESIGN.md` 側で扱う設計上の欠落を列挙してリンクする。

### 1 項目の型

```markdown
<a id="i-1"></a>
## I-1. 症状が分かる短い題

**深刻度: 高**（外部から誘発可能）

### 症状
何が観測されるか。ログに出るのか、静かに壊れるのか。

### 該当箇所
ファイルへの行番号付きリンクと、必要ならコードの引用。

### 原因
なぜそうなっているか。

### 影響
どこまで壊れるか。他の項目との依存。いま顕在化していないならその理由。

### 対応方針
直し方。再発防止の提案（テスト、型、マクロによる検出）まで含めてよい。
```

5 節すべてを書く。
`<a id="i-1"></a>` の明示アンカーを置く。
日本語見出しの自動アンカーは長く、題を直すと壊れるためである。

ID は再利用しない。
削除した ID は欠番のままにする。

### 深刻度

3 段階で、次の基準で判定する。

- **高**：その経路の機能が成立しない、データを壊す、外部からの入力で停止させられる、のいずれか。
- **中**：現時点では結果が変わらないが条件が揃うと壊れる、または設計判断が決まらないと直せない。
- **低**：実害はないが読む人を誤解させる、または品質上の負債である。

深刻度の直後に、顕在性を括弧で必ず添える。
いま実際に壊れているものには何も付けない。
壊れていないものには、なぜ今は壊れていないのかを短く書く（「現時点では未顕在」「設計論点に依存」）。
逆に、深刻度が中や低でも外部から誘発できるものはそう書く。

顕在性は深刻度と直交する。
「未結線ゆえに安全」な項目と、そうでない項目を区別できるようにしておく。

### ライフサイクル

- 起票したら、一覧表の Issue 列に番号を追記する。項目本体は残す
- 修正されたら、項目ごと削除する。一覧表の行も消す
- ここに残っているものは未対応、が原則である

## 根拠の出所を区別する

3 つに分けて書く。

**コードで確認した事実**は、そのまま断定して書く。

**コードから読み取った意図**は、出所を明示する。
「という意図に読める（コード上に理由の記述はない）」のように、推測であることを文中に残す。
有用な推察を捨てる必要はないが、事実として書いてはいけない。

**確認できていないこと**は本文に書かない。
設計判断章の保留に回すか、`ISSUES.md` に回す。
検証していない挙動を現在形で書くと、文書が嘘をつく。

## 文体と表記

- 一文ごとに改行する。段落の区切りは空行で示す
- 半角英数字の前後に半角スペースを入れる（「Rust 製の daemon」）
- 数値と単位の間にも半角スペースを入れる（`32 MiB`、`30 分`、`1024 件`）
- 節への参照は `§7.3` の形で書く。数字だけでは節番号か数値か判別できない
- ダッシュ（em ダッシュ `—`、horizontal bar `―`、2 倍ダッシュ「——」）を日本語の地の文と見出しで使わない。同格や補足の挿入は括弧に、言い換えは句点で二文に分ける
- 用語とその定義を並べる箇条書きは、全角コロンで「**用語**：説明」と書く
- 中黒（・）を日本語の並列で使わない。単一の固有名詞の内部では使ってよい
- 見出しに区切り線で二要素を詰め込まない。単一の自然な句にする

太字は次の 3 用途に限る。

1. 設計判断や ISSUES の項目における、定義ブロックのラベル（`**決定**`、`**深刻度: 高**`）
2. 用語を本文中で初めて定義するとき
3. 1 節に 1 つだけ、見落とすと設計を誤る前提（`**この設計には満たすべき前提がある。**`）

強調のための太字を散らさない。
1 節に太字が 4 つ以上あれば、どれも目に入らなくなっている。

## 図

図種を用途で固定する。

| 用途 | 記法 |
| --- | --- |
| 依存関係、処理の流れ | mermaid `flowchart` / `graph` |
| コンポーネント間のやり取りの順序 | mermaid `sequenceDiagram` |
| 状態遷移 | mermaid `stateDiagram-v2` |
| 層の重なり、ディレクトリツリー | コードブロックの ASCII |

層とツリーを mermaid で描かない。
ASCII のほうが読みやすく、行の追加で崩れない。

**図の直前か直後に、図から読み取れない設計上の含意を 1 文添える。**
「依存の向きは一方向である。ただしこの 1 本だけが横方向の依存になっている」「web は daemon と同じプロセス、同じポートから配信される。この前提が §9.5 の CSRF 対策を成立させている」のような文である。
この一文がない図は飾りであり、削ってよい。

## 参照とリンク

**DESIGN.md からコードへの参照**は、ファイル単位のリンクまでとする。
行番号（`#L42`）を書かない。
意味論を書く文書が行番号で腐るのは割に合わない。
位置を特定したいときは、型名や関数名で指す。

**ISSUES.md からコードへの参照**は、行番号付きのリンクを必須とする。
この文書は調査日と対象コミットを明記したスナップショットであり、腐ることが前提である。
該当箇所の特定が目的なので、行番号を省かない。

文書間のリンクは相対パスで書く。
`DESIGN.md` の節を指すときは、見出しのアンカーまで含める。

## 執筆後の点検

書き終えたら次を機械的に確認する。

1. 実装状況の記述が、現状と残作業章と `ISSUES.md` の外に漏れていないか。「未実装」「未着手」「未結線」で検索する
2. 保留項目すべてに「決める条件」があるか
3. `DESIGN.md` に行番号付きリンクがないか。`rg '#L[0-9]' docs/DESIGN.md` が空であること
4. `ISSUES.md` に調査日と対象コミットがあるか
5. すべての図の直前か直後に、含意の一文があるか
6. 地の文と見出しにダッシュがないか。`rg '[—―]' docs/*.md` を確認する（コードブロックと範囲を示す en ダッシュは対象外）
7. 一文一行になっているか。1 行に句点が 2 つ以上ある箇所を探す
8. 節参照が `§` 付きか
9. 他文書が正であるものを複写していないか。API のパス一覧、フィールド番号、`TODO` の一覧が入り込んでいないか
10. 推測を断定で書いていないか。理由を述べている箇所が、コードのどこに根拠があるか言えるか

## 付録：daemon 型リポジトリでの各論章の例

daemon と engine と生成された interface で構成され、API 定義ファイルを契約の正とするリポジトリでは、各論章は次の並びになる。
これは例であり、そのまま使う必要はない。

```
5. daemon の内部構造
   5.1 層構造（各層が何を知らないかを書く）
   5.2 API 定義からのコード生成
   5.3 エラーモデルと HTTP 対応
6. ストレージ層
   6.1 ファサードと driver の連鎖
   6.2 各 driver
   6.3 書き込みの原子性（前提と、崩れる条件）
7. （ドメイン固有の機能）
8. 認証とセッション
   8.1 初期セットアップ
   8.2 セッションの運搬と保管
9. 変更系 API の規約
   9.1 名前空間
   9.2 同期と非同期の判定（表）
   9.3 競合ポリシー
   9.4 長時間操作の状態遷移
10. 設定と永続化
   10.1 設定ファイル
   10.2 状態の置き場（消えたときの影響を列に持つ表）
11. クライアント
```

各論の粒度の目安は次の 2 点である。

- 1 章が扱うのは 1 つの層か 1 つの機能。層をまたぐ章を作らない
- 「〜の規約」章は、複数のエンドポイントや操作に横断する判断基準がある場合にだけ立てる
