# 不具合一覧

`docs/issues.md` を書くとき、直すとき、点検するときは、本書に従う。
文書族の責務、文体、図、情報密度、根拠の扱い、リンク規約は [共通規範](../SKILL.md) に従い、本書では不具合一覧に固有の点だけを定める。

本書が扱うのは、コードを読んで確認した明確な不具合だけである。
何を選ぶかがまだ決まっていないものは設計論点であり、その関心事を受け持つ設計文書の設計判断章に書く。

## 3 つのモード

**新規作成**：コードを読んで調査し、調査日と対象コミットを固定してから項目を書く。

**更新**：項目の追加、起票した Issue 番号の追記、修正された項目の削除。
調査日と対象コミットを更新するときは、既存項目の該当箇所を再確認する。

**点検**：§「執筆後の点検」を機械的に走らせ、本文は変更せず所見と根拠だけを報告する。

## 保持する意味要素

共通規範の §「情報密度」に従い、圧縮しても次を残す。

- 調査日と対象コミット
- 各項目の症状、該当箇所、原因、影響、対応方針
- 深刻度と顕在性
- 項目間の関係
- ここに含めていないもの

## 検証用サブエージェント

共通規範の §「検証用サブエージェント」に従い、新規作成と項目の追加で `verifier` を必須とする。
起票した Issue 番号の追記と、修正された項目の削除だけなら要さない。
点検では本文を変更しないため要さない。

blocking とする指摘に次を追加する。

- 項目に 5 節のいずれかがない
- 深刻度に顕在性が添えられていない
- 該当箇所に行番号がない
- 調査日または対象コミットがない
- 設計論点が項目として混ざっている

## 全体の形

冒頭に次を置く。

1. この文書が扱うもの（確認した明確な不具合のみ）と、扱わないもの（設計論点は該当する設計文書の設計判断章）
2. 使い方（起票したら Issue 番号を追記、修正されたら項目ごと削除、行番号はずれるので修正時に再確認）
3. 調査日と対象コミット

調査日と対象コミットは必須である。
この文書はスナップショットであり、いつ時点の情報かが分からないと使えない。

§1.1 には完全な地図を持たず、本書が受け持つものと置かないものを書き、文書族の地図は `[design.md](./design.md#11-文書間の責務分担)` へリンクする。

続いて一覧表を置く。
列は ID、概要、深刻度、Issue の 4 つ。
ID は項目へのアンカーリンクにする。

表の下に、項目間の関係を 1 段落で書く。
同じ経路にある項目、まとめて直すのが効率的な項目を指摘する。

末尾に「ここに含めていないもの」の表を置き、設計文書側で扱う設計上の欠落を列挙してリンクする。

## 1 項目の型

```markdown
<a id="i-1"></a>
## I-1. 症状が分かる短い題

**深刻度: 高**（外部から誘発可能）

### 症状
何が観測されるか。ログに出るのか、静かに壊れるのか。

### 該当箇所
ファイルへの行番号付きリンクと、必要ならコードの引用。

### 原因
なぜそうなっているか。

### 影響
どこまで壊れるか。他の項目との依存。いま顕在化していないならその理由。

### 対応方針
直し方。再発防止の提案（テスト、型、マクロによる検出）まで含めてよい。
```

5 節すべてを書く。
`<a id="i-1"></a>` の明示アンカーを置く。
日本語見出しの自動アンカーは長く、題を直すと壊れるためである。

ID は再利用しない。
削除した ID は欠番のままにする。

## 深刻度

3 段階で、次の基準で判定する。

- **高**：その経路の機能が成立しない、データを壊す、外部からの入力で停止させられる、のいずれか。
- **中**：現時点では結果が変わらないが条件が揃うと壊れる、または設計判断が決まらないと直せない。
- **低**：実害はないが読む人を誤解させる、または品質上の負債である。

深刻度の直後に、顕在性を括弧で必ず添える。
いま実際に壊れているものには何も付けない。
壊れていないものには、なぜ今は壊れていないのかを短く書く（「現時点では未顕在」「設計論点に依存」）。
逆に、深刻度が中や低でも外部から誘発できるものはそう書く。

顕在性は深刻度と直交する。
「未結線ゆえに安全」な項目と、そうでない項目を区別できるようにしておく。

## ライフサイクル

- 起票したら、一覧表の Issue 列に番号を追記する。項目本体は残す
- 修正されたら、項目ごと削除する。一覧表の行も消す
- ここに残っているものは未対応、が原則である

レビュー結果文書から転記された項目も同じ扱いにする。
転記元へのリンクは張らない。
出所をたどりたいときは ID で `docs/reviews/` を検索すれば足りる。

## 書かないこと

**設計論点**は該当する設計文書の設計判断章が持つ。
何を選ぶかが決まっていないものを不具合として起票しない。

**語の定義**は `terms.md` が持つ。
名前が揃っていないこと自体を不具合として書くときも、正しい名前は `terms.md` を指す。

**レビューの経緯**は `docs/reviews/<slug>.md` が持つ。
誰がいつ見つけたかは本書に書かない。

## 執筆後の点検

共通規範の §「共通の執筆後の点検」に加えて、次を確認する。

1. 調査日と対象コミットがあるか
2. すべての項目に、症状、該当箇所、原因、影響、対応方針の 5 節があるか
3. すべての項目に明示アンカーがあり、一覧表の ID と 1 対 1 か
4. すべての深刻度に顕在性が括弧で添えられているか
5. 該当箇所のコードへの参照に行番号があるか
6. 一覧表の下に項目間の関係の段落があるか
7. 末尾に「ここに含めていないもの」の表があり、設計文書へのリンクが見出しのアンカーまで含んでいるか
8. 設計論点、語の定義、レビューの経緯が混ざっていないか
9. 削除した ID が再利用されていないか
