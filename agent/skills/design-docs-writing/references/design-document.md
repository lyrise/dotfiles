# 設計文書

`docs/design.md` を入口とする設計文書群を書くとき、直すとき、分割するとき、点検するときは、本書に従う。
文書族の責務、文体、図、情報密度、根拠の扱い、リンク規約は [共通規範](../SKILL.md) に従い、本書では設計文書に固有の点だけを定める。

設計文書は語を定義しない。
語の定義、表記、別称、隣接語との境界は [用語文書](terms-document.md) が正本であり、設計文書はその語彙を前提として使う。

## 3 つのモード

**新規作成**：コードを読み、`design.md` の骨格（§「design.md の章立て」）を先に立て、各章を埋める。
同時に `docs/terms.md` を作り、本文で使う語をそちらに定義する。
確認できなかったことは埋めない。

**更新**：設計判断が変わったとき、または圧縮か分割を明示的に依頼されたときに本文を触る。
実装が進んだだけのときは、本文を書き換えず、現状と残作業章と `issues.md` だけを直す。

**点検**：§「執筆後の点検」のチェックリストを機械的に走らせる。
本文は変更せず、圧縮候補と分割候補を含む所見と根拠だけを報告する。

## 保持する意味要素

共通規範の §「情報密度」に従い、圧縮しても次を残す。

- 責務と境界
- 不変条件、その前提、崩れる条件
- 決定、理由、実際に検討した却下案
- 保留事項の現状、今決めない理由、決める条件
- 実装状況、依存関係、残作業

## 検証用サブエージェント

共通規範の §「検証用サブエージェント」に従い、新規作成と更新で `verifier` を必須とする。
blocking とする指摘に次を追加する。

- 語の定義が設計文書に混ざっている
- 分割後の正本の重複、入口から到達できない詳細文書、責務の欠落
- 実装状況が現状と残作業章の外に漏れている
- 決める条件のない保留

## design.md の章立て

先頭 3 章と末尾 2 章は、この順序で必須である。
中間の各論章はプロジェクトによって変わる。

```
1. このドキュメントについて
   1.1 文書間の責務分担
   1.2 本書の時制について
2. 〇〇とは / スコープ外
   2.1 スコープ外
3. 全体構成
   3.1 コンポーネントとディレクトリ対応表
   3.2 処理の流れ

--- 各論（プロジェクト依存、章数も見出しも自由） ---
4. …
N. …

--- 末尾 ---
N+1. 設計判断
   N+1.1 決定済み
   N+1.2 保留
N+2. 現状と残作業
```

見出しには `## 1.` `### 1.1` の形で番号を振る。
`####` には番号を振らない。

用語集の章を置かない。
各論を読む前に語彙が揃っている必要があるが、それを満たすのは本書の一章ではなく `terms.md` である。

### 1. このドキュメントについて

何を扱う文書か、想定読者は誰かを 2 文から 3 文で述べる。
そのうえで「本書は [terms.md](./terms.md) の語彙を前提とする。語の定義は本書にない」の 1 行を置く。

**1.1 文書間の責務分担**は表で書く。
この節は必須であり、文書族のなかで完全な地図を持つ唯一の場所である。
このリポジトリで何がどの文書の正なのかを、`docs/design/*.md`、`terms.md`、`issues.md`、API 定義ファイル、`README.md` まで含めて列挙する。
そのうえで、本書に置かないものを明示する。

`本書` だけを非リンクにし、ほかの文書名はすべて実体への相対 Markdown リンクにする。
`[terms.md](./terms.md)`、`[issues.md](./issues.md)`、リポジトリ直下は `[README.md](../README.md)` の形で書く。

**1.2 本書の時制について**では、本文が完成形を現在形で書かれていることと、実装状況は現状と残作業章にあることを述べる。
「いま何が動くのかを知りたい場合は N 章を先に読む」の 1 行を必ず置く。

### 2. 〇〇とは / スコープ外

何をするものか、想定する運用（規模、利用者数、公開範囲）を述べる。

**2.1 スコープ外**には、作らないと決めたものを列挙する。
そのうえで、それを外したことで持たずに済んでいる機構を書く。
「共有リンクを作らないので権限モデルを持たない」のように、スコープ外の決定と設計の単純さを結び付ける。
この一文があると、後からスコープを広げる提案の代償が読める。

### 3. 全体構成

**3.1** はディレクトリとコンポーネントの対応表にする。
各行に、パス、パッケージ名、役割を書く。
パス列の表示文字列はリポジトリルートからの相対パスにし、リンク先は `docs/design.md` から実体への相対パスにする。
たとえば `[daemon/entrypoints/daemon](../daemon/entrypoints/daemon)` と書く。
自動生成物には「手で編集しない」と表中に明記する。

**3.2** は処理の流れの図を置く。

### 各論章

1 章に 1 つの関心事を置く。
層、機能、規約のいずれかである。

各節では、何をするかの前に、なぜその形かを書く。
形だけを書いた節はコードの重複であり、価値がない。

不変条件は、それが成り立つ前提とともに書く。
前提が崩れる条件まで書く。
たとえば「rename でアトミックに公開する」と書くなら、同一ファイルシステム内でしか成り立たないことと、別ファイルシステムだとどう壊れるかを続けて書く。

各論の粒度の目安は次の 2 点である。

- 1 章が扱うのは 1 つの層か 1 つの機能。層をまたぐ章を作らない
- 「〜の規約」章は、複数のエンドポイントや操作に横断する判断基準がある場合にだけ立てる

### 設計判断章

**決定済み**は `####` 見出しで 1 決定ずつ、次の型で書く。

```markdown
#### 決定の要約を体言止めか終止形で

**決定**
何を決めたか。実装ではなく約束を書く。

**理由**
なぜそれを選んだか。何を優先し、何を諦めたか。

**却下案**
検討して退けた案と、退けた理由。
```

**却下案**は、検討した案があるときだけ書く。
なかった決定には節を置かない。
ただし、コードや依存関係に一度採用した痕跡が残っている案は必ず書く。
書いておかないと、後から同じ案が再提案される。

命名をどうするかの判断はここに書かない。
退けた名前とその理由は `terms.md` が持つ（[用語文書](terms-document.md)）。

**保留**は `####` 見出しで 1 項目ずつ、次の型で書く。

```markdown
#### 保留している論点

**現状**
いまどうなっているか。

**なぜ今決めないか**
決めずに済んでいる理由。

**決める条件**
何が起きたら決めるか。
```

**決める条件**は必須である。
これがない項目は保留ではなく放置であり、書く意味がない。
条件は観測可能な事象で書く（「LAN 外からのアクセスを実際に必要としたとき」「検索が実運用のツリーサイズで使い物にならなくなったとき」）。

選択肢が複数ある保留では、選択肢を番号付きで列挙し、それぞれの代償を 1 文添える。

### 現状と残作業章

実装状況をこの章にだけ書く。
本文の各節に状態の注記を散らさない。
先頭に実装状況のサマリ表も置かない。
状態を 2 箇所以上に書くと、必ず片方が腐る。

**ロードマップ**は表で書く。
順序は暫定であると明記し、守る必要があるのは依存関係だけであると述べる。
表の列は、番号、内容、前提とする依存の 3 つを基本とする。

不具合は書かない。
章の末尾に `[issues.md](./issues.md)` の形で導線を 1 行置く。

### 設計文書に書かないこと

**他に唯一の正があるものを複写しない。**
語の定義と表記は `terms.md` が持つ。
API のパスやステータスコードの網羅的な一覧は API 定義ファイルが持つ。
バイト列のレイアウト、シリアライズのフィールド番号、エンコーディングの詳細はコードが持つ。
セットアップ手順と依存パッケージは `README.md` が持つ。

**機械的に引けるものを書かない。**
未実装箇所の一覧、`TODO` の一覧、ファイル一覧は書かない。
代わりに引き方を 1 行書く（「未実装箇所の現物は `rg 'todo!' src` で引ける」）。

例外は、表の形でしか全体を把握できない横断的な規約に限る。
「どの操作が同期でどれが非同期か」「エラー種別と HTTP ステータスの対応」のように、判断基準として一望する必要があるものは、複写ではなく規約の提示として書いてよい。
その場合、個々の定義は元の文書を見ることを明記する。

## 分割

### 分割の判断

まず §「保持する意味要素」と共通規範の §「情報密度」に従って重複、正本の複写、内容のない定型文を除く。
それでも残る各論のうち、独立した責務と境界を持ち、ほかの各論と常に一緒に読む必要がない関心事だけを分割する。
行数、文字数、トークン数だけを分割理由にしない。

新規作成では単一の `docs/design.md` を既定とする。
点検では分割候補と根拠だけを報告し、更新の依頼なしに分割しない。

### 配置と命名

`docs/design.md` を設計文書群の唯一の入口として残し、詳細文書を `docs/design/<slug>.md` に置く。
`<slug>` は関心事を表す安定した英小文字の kebab-case とし、章番号を含めない。
章の追加や並び替えでファイル名とリンクを変えないためである。
詳細文書をさらに子ディレクトリへ分割しない。

```text
docs/
├── design.md
├── terms.md
├── issues.md
└── design/
    ├── authentication.md
    ├── storage.md
    └── task-execution.md
```

### 分割後の責務分担

| 文書 | 受け持つもの |
| --- | --- |
| `docs/design.md` | プロジェクト全体のスコープ、全体構成、関心事間の境界、横断的な設計判断、全体の依存関係 |
| `docs/design/<slug>.md` | 1 つの関心事に閉じる責務と境界、不変条件、設計詳細、設計判断、現状と残作業 |

1 つの事実、判断、保留事項には正本を 1 つだけ定める。
横断的な内容は `docs/design.md`、1 つの関心事に閉じる内容は詳細文書に置く。

語の定義はどちらにも置かない。
`terms.md` が語彙の唯一の正本であり、関心事に閉じる語は `terms.md` のスコープ列で所属を示す。

`docs/design.md` の各論には、分割した関心事の目的、境界、ほかの関心事との関係が分かる要約と詳細文書への相対リンクだけを残す。
詳細、不変条件、判断、保留、実装状況を複写しない。
全体の現状と残作業章は関心事間の依存だけを持ち、詳細文書の実装状況を言い直さない。

`docs/design.md` の §1.1 に、すべての詳細文書と、各文書で分かることを列挙する。
詳細文書は §1.1 から `docs/design.md` へ相対リンクし、自身が受け持つ範囲と受け持たない範囲を明示する。

### 詳細文書の章立て

`design.md` の章立てとの差分は 2 点である。
第 2 章が「責務と境界」になり、全体構成章を持たない。
章番号は詳細文書内で閉じ、`docs/design.md` の章番号を引き継がない。

```text
1. このドキュメントについて
   1.1 文書間の責務分担
   1.2 本書の時制について
2. 責務と境界

--- 各論（関心事依存） ---
3. …
N. …

--- 末尾 ---
N+1. 設計判断
   N+1.1 決定済み
   N+1.2 保留
N+2. 現状と残作業
```

`1.1` では完全な地図を持たず、`docs/design.md`、この関心事と境界を接する詳細文書、API 定義などとの境界を相対リンク付きで示す。
`1.2`、各論章、設計判断章、現状と残作業章には `docs/design.md` と同じ規範を適用する。
不具合への導線は詳細文書から見た相対パスで `[issues.md](../issues.md)` と書く。

### 既存文書の移行

1. 移動対象の各節、設計判断、保留、現状と残作業、リポジトリ内からの参照を列挙する。
2. 各意味要素の移動先を 1 つ決め、内部の対応表を作る。対応表は成果物に残さない。
3. 詳細だけでなく、その関心事に閉じる理由、不変条件、判断、保留、実装状況を一緒に移す。
4. 元の各論見出しを残し、目的、境界、ほかの関心事との関係を示す要約と詳細文書へのリンクへ置き換える。
5. `docs/design.md` の §1.1 と全体の依存関係を更新する。
6. リポジトリ内の参照を検索し、移動した見出しへのリンクを新しいファイルとアンカーへ更新する。

既存の見出しを削除または改名する必要がある場合は、先にリポジトリ内の参照をすべて確認する。
外部から参照される可能性がある見出しは、`docs/design.md` 側の要約見出しとして維持する。

### 分割の検証

分割は圧縮ではなく構造の更新として扱う。
分割前後の文書群全体の文字数と行数を測るが、導線、責務分担、時制の追加による増加だけを許容し、その増分を報告する。
圧縮も同時に依頼された場合は、移動した本文の削減量と分割に必要な増分を分けて測る。

機械検査と `verifier` で次を確認する。

1. 移動前の責務、境界、不変条件と崩れる条件、判断、却下案、保留、実装状況、依存関係、残作業が失われていない
2. 各意味要素の正本が 1 つであり、`docs/design.md` と詳細文書で本文を重複していない
3. すべての詳細文書が `docs/design.md` から到達でき、詳細文書からも入口へ戻れる
4. 横断的な内容と関心事内の内容が責務分担どおりに置かれている
5. リポジトリ内の既存リンク、見出しアンカー、各文書を基準にした相対リンクが壊れていない
6. 設計文書にコードの行番号リンクがなく、実装状況が各文書の現状と残作業章以外に漏れていない
7. `issues.md` から移動対象を指すリンクが、新しい詳細文書の見出しまで含んでいる
8. 移動の過程で語の定義が詳細文書に紛れ込んでいない

## 執筆後の点検

共通規範の §「共通の執筆後の点検」に加えて、次を確認する。

1. 実装状況の記述が、各設計文書の現状と残作業章と `issues.md` の外に漏れていないか。「未実装」「未着手」「未結線」で検索する
2. 保留項目すべてに「決める条件」があるか
3. 語の定義が設計文書に混ざっていないか。用語集の章や、語の意味を定義している段落が残っていないか
4. 第 1 章に `terms.md` を前提とする 1 行があるか
5. `design.md` の §1.1 が完全な地図になっており、詳細文書の §1.1 が委譲先だけを書いているか
6. 他文書が正であるものを複写していないか。API のパス一覧、フィールド番号、`TODO` の一覧が入り込んでいないか
7. 圧縮前の意味要素が圧縮後のどこに残ったか、変更した節ごとに内部で照合したか。対応表は文書に残さない
8. 圧縮直前と圧縮後の文字数と行数を測り、圧縮後が増えていないか
9. 分割した場合は、§「分割の検証」の 8 項目をすべて満たしたか

## 付録：daemon 型リポジトリでの各論章の例

daemon と engine と生成された interface で構成され、API 定義ファイルを契約の正とするリポジトリでは、各論章は次の並びになる。
これは例であり、そのまま使う必要はない。

```
4. daemon の内部構造
   4.1 層構造（各層が何を知らないかを書く）
   4.2 API 定義からのコード生成
   4.3 エラーモデルと HTTP 対応
5. ストレージ層
   5.1 ファサードと driver の連鎖
   5.2 各 driver
   5.3 書き込みの原子性（前提と、崩れる条件）
6. （ドメイン固有の機能）
7. 認証とセッション
   7.1 初期セットアップ
   7.2 セッションの運搬と保管
8. 変更系 API の規約
   8.1 名前空間
   8.2 同期と非同期の判定（表）
   8.3 競合ポリシー
   8.4 長時間操作の状態遷移
9. 設定と永続化
   9.1 設定ファイル
   9.2 状態の置き場（消えたときの影響を列に持つ表）
10. クライアント
```
