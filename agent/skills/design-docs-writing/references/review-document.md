# レビュー結果文書

`docs/reviews/<slug>.md` を書くとき、点検するとき、指摘を転記するときは、本書に従う。
文書族の責務、文体、図、情報密度、根拠の扱い、リンク規約は [共通規範](../SKILL.md) に従い、本書ではレビュー結果文書に固有の点だけを定める。

この規範が守るのは 3 点である。
読む人が、見た範囲と見ていない範囲を取り違えないこと。
見つかった指摘が、どこにも拾われないまま消えないこと。
修正が終わった後も、いつ何をどの観点で見たかが残ること。

## 2 つのレビュー

**差分レビュー**は、PR、ブランチ、作業ツリーの変更を対象とする。
範囲は差分が決めるので、差分の外はすべて見ていない範囲である。

**監査レビュー**は、差分ではなく既存コードの特定の領域を通しで読む。
範囲を自分で切るので、どこで切ったかとその基準を書かなければ、見ていない範囲が定まらない。

どちらであるかを §1.2 で宣言する。
章立ては共通で、分岐するのは §2.1 の書き方だけである。

1 つの文書で両方を扱わない。
差分の外まで読んだなら、それは 2 回のレビューであり、2 つの文書にする。

## slug と索引

`<slug>` は `YYYY-MM-DD-<対象>` の形にする。
`<対象>` はレビューした範囲を指す kebab-case の短い名前にする（`2026-08-10-storage-facade`、`2026-08-10-pr-142`）。

日付を前に置く理由は 2 つある。
恒久保存なので件数が増え、時系列に並ぶこと自体が索引になる。
同じ範囲を後日あらためてレビューしたときに、ファイル名が衝突しない。

索引ファイルは作らない。
ファイル名の一覧が索引であり、機械的に引けるものを文書にしない。

## 3 つのモード

**新規作成**：レビューを実施した直後に、章立て（§「章立て」）を立てて各章を埋める。
日をまたぐと、何を確かめて何を確かめていないかを思い出せなくなり、§2.2 と確度が書けなくなる。

**追記**：発行済みの文書に対して、§6 にだけ日付付きで書き足す（§「不変性」）。
§1 から §5 は触らない。

**点検**：§「執筆後の点検」を機械的に走らせ、本文は変更せず所見と根拠だけを報告する。

指摘を恒久文書へ移す作業は、モードではなく発行後の必須手続きである（§「転記」）。

## 不変性

発行した後は §1 から §5 を書き換えない。

レビュー結果文書はその時点の判断の記録である。
後から書き換えると、レビュー時点で何を知っていたかが分からなくなり、記録としての価値が消える。
実装計画書と違って畳まないのも同じ理由による。

書き換えてよいのは誤字と壊れたリンクだけであり、事実の記述と判断は直さない。
指摘が誤りだったと後で分かったときも、§4 の本文は残したまま、§6 に「R-3 は誤りだった」と理由を添えて追記する。
消すと、なぜその指摘が出たのかを次のレビューが繰り返す。

## 保持する意味要素

共通規範の §「情報密度」に従い、圧縮しても次を残す。

- レビューの型、対象コミット、レビュー日、レビュアー
- 見た範囲と、見ていない範囲と、見なかった理由
- 探した観点
- 全体としての判断
- 各指摘の該当箇所、問題、根拠、影響、扱い
- 疑って確かめ、問題がないと判断した対象と、その判断の根拠
- 発行後に起きたこと

次の記述は追加で削除または統合してよい。

- 変更内容の要約（git が正本である）
- 指摘の題を言い直しただけの「何が問題か」
- 総評での指摘本文の再掲

## 検証用サブエージェント

共通規範の §「検証用サブエージェント」に従い、`verifier` を必須とする範囲を次に置き換える。

新規作成では必須とし、利用できない場合は文書を作らないで報告する。
§6 への追記と点検では要さない。
転記では、移し先の恒久文書の変更に、それぞれの reference の必須範囲が適用される。

blocking とする指摘を次に置き換える。

- §2.2 が空、または「なし」で済まされている
- 観点が列挙されていない
- 指摘に扱いがない
- 確度が根拠と食い違っている（確かめていないものを確度 高 にしている）
- 該当箇所に行番号がない
- 種別が 4 つのいずれでもない、または種別と転記先が対応していない
- 転記先の識別子がリンクになっている
- 差分の要約または修正コードの貼り付け
- 発行済み文書の §1 から §5 への変更
- 見出し、アンカー、リンクの破損

## 章立て

```
1. このレビューについて
   1.1 文書間の責務分担
   1.2 レビュー日と対象
2. 範囲と観点
   2.1 見た範囲
   2.2 見ていない範囲
   2.3 観点
3. 総評
4. 指摘
5. 確かめて問題がなかったこと
6. その後
```

6 章すべて必須である。
見出しには `## 1.` `### 1.1` の形で番号を振り、`####` には振らない。

### 1. このレビューについて

何のレビューかを 1 文から 2 文で述べる。

**1.1 文書間の責務分担**は表で書く。
完全な地図は持たず、本書が受け持つもの、本書に置かないもの、転記先となる文書だけを列挙する。
文書族の地図は `[design.md](../design.md#11-文書間の責務分担)` へのリンクで示す。
転記先は `[terms.md](../terms.md)`、`[issues.md](../issues.md)`、該当する設計文書を指す。

**1.2 レビュー日と対象**は必須で、次の 4 つを書く。

1. レビュー日
2. レビューの型（差分レビューか監査レビューか）
3. 対象コミット。差分レビューでは base と head の両方を書き、PR 番号があれば併記する
4. レビュアー。人間なら名前、エージェントならモデル名を書く

レビュアーを書くのは、誰が見たかで指摘の読み方が変わるためである。
複数で見たなら全員を書く。

### 2. 範囲と観点

**2.1 見た範囲**は、レビューの型で書き方が分かれる。

差分レビューでは、base と head の間で変更されたファイルのうち、実際に読んだものを書く。
差分の全ファイルを読んだなら、そう 1 行で書く。
読んでいないファイルがあるなら §2.2 に回す。

監査レビューでは、読んだディレクトリまたはモジュールと、範囲をそこで切った基準を書く。
基準を書かないと、隣接する領域を意図して外したのか見落としたのかが読み取れない。

**2.2 見ていない範囲**は必須であり、空にしない。
「なし」「特になし」と書くことを禁じる。
差分レビューであれば、少なくとも差分の外は見ていない。

各項目に、見なかった理由を添える。
範囲外だから、別のレビューで扱うから、時間が足りなかったから、のいずれかである。
最後の理由を隠さない。

この節がないと、レビュー済みという事実が全体の保証として誤読される。
レビュー結果文書がいちばん強く主張すべきなのは、見つけたものではなく、見ていない範囲である。

**2.3 観点**には、何を探したかを列挙する。
観点に載っていないものは探していないのであり、§2.2 の一部である。

観点を書かないレビューでは、指摘が 0 件だったことの意味が定まらない。
何も探さなくても 0 件になる。

観点の立て方は §「付録：観点の例」を見る。

### 3. 総評

全体としての判断を 2 文から 4 文で書く。

差分レビューでは、このまま進めてよいか、直してから進めるか、設計を決め直す必要があるかを 1 文で明記する。
監査レビューでは、その領域が現状のまま使えるかどうかを 1 文で明記する。

深刻なものがあるなら ID で指し、指摘の本文を再掲しない。

### 4. 指摘

冒頭に一覧表を置く。
列は ID、概要、種別、確度、扱いの 5 つで、ID は項目へのアンカーリンクにする。
表の下に、項目間の関係を 1 段落で書く。
同じ原因から出ている項目、まとめて直すのが効率的な項目を指摘する。

指摘が 0 件なら、表を置かず「指摘なし」と 1 文だけ書く。
このとき §2.2 と §5 が文書の実質になる。

各指摘は次の型で書く。

```markdown
<a id="r-1"></a>
### R-1. 症状が分かる短い題

**種別: 不具合** / **確度: 高**

**該当箇所**
行番号付きリンクと、必要ならコードの引用。

**何が問題か**
何が起きるか。題の言い直しにしない。

**根拠**
なぜそう言えるか。確かめたことと、確かめていないことを分けて書く。

**影響**
どこまで壊れるか。いま顕在化していないならその理由。

**扱い**
転記先の文書と識別子。転記しないなら、その理由。
```

5 つのラベルすべてを書く。
`<a id="r-1"></a>` の明示アンカーを置く。
日本語見出しの自動アンカーは長く、題を直すと壊れるためである。

ID は `R-` で始め、`issues.md` の `I-` と混ざらないようにする。
1 つの文書の中で連番とし、削除した ID は欠番のままにする。

**種別**は次の 4 つとし、共通規範の §「文書族と責務」と同じ境界で判定する。

- **不具合**：何をどう直すか分かっているもの
- **設計論点**：何を選ぶかがまだ決まっていないもの
- **用語**：語の定義、表記、別称が揃っていない。コードが同じものを 2 つの名前で呼んでいる、`terms.md` と実装の識別子が食い違う、退けたはずの別称が新しいコードに現れた
- **改善提案**：壊れてはいないが、より良くできるもの

種別が転記先を決める（§「転記」）。
1 つの指摘に 2 つの種別を付けない。
付けたくなったら、それは 2 つの指摘である。

**確度**は 3 段階で、次の基準で判定する。

- **高**：コードを読み、その経路が実際にそうなることを確認した
- **中**：そうなる条件を特定したが、その条件が成立するかは確認していない
- **低**：不審だが、成立するかどうかを確かめていない

確度 低 の指摘を書いてよい。
恒久文書が確認できていないことを本文に書かないのに対して、レビュー結果文書は疑いを記録することが役割だからである。
ただし確度を偽らない。
確かめていないものを 高 と書いた時点で、この文書は読み手に嘘をつく。

根拠と確度は必ず食い合わせる。
根拠に「と思われる」「はずである」と書いてあるのに確度が 高 なら、どちらかが間違っている。

### 5. 確かめて問題がなかったこと

疑って確かめ、問題がないと判断したものだけを書く。
1 項目 1 行から 2 行で、何を疑い、何をもって否定したかを書く。

読んだが疑いを持たなかった箇所は書かない。
それは §2.1 の範囲がすでに表している。
ここに読み流した箇所を並べると、確かめたことと読んだだけのことが混ざり、章の意味が消える。

この章がないと、指摘 0 件のレビューと、何も見ていないレビューを区別できない。

### 6. その後

発行後に起きたことを、日付付きの箇条書きで追記する。
発行時点では見出しだけを置き、中身が空でよい唯一の章である。

```markdown
- 2026-08-12: R-1 を issues.md に I-7 として起票
- 2026-08-15: R-2 は誤りだった。`flush` は呼び出し元で保証されており、この経路では起きない
- 2026-08-20: R-3 を修正。issues.md の I-8 は削除済み
```

書くのは、転記したこと、修正されたこと、判断が覆ったことの 3 つである。
実装の進捗はここに書かない。
それは実装計画書と git の履歴が正である。

## 転記

発行したら、指摘を転記する。
転記しないと、この文書だけが持つ指摘になり、修正の流れに乗らない。
恒久保存なので放っておいても消えないが、誰も見ない。

| 種別 | 転記先 | 転記しないでよい場合 |
| --- | --- | --- |
| 不具合 | `issues.md` に 1 項目として起票 | 同じレビューの中で直したとき |
| 設計論点 | 該当する設計文書の設計判断章の保留（決める条件を必ず付ける） | なし |
| 用語 | `terms.md` の用語一覧または個別の用語 | 同じレビューの中で直したとき |
| 改善提案 | `issues.md` に深刻度 低 で起票 | やらないと決めたとき |

転記しない場合も、**扱い**の欄を空にしない。
「同じレビューの中で修正済み」「やらないと決めた。理由は〜」と書く。
扱いが空の指摘は、誰にも拾われずに消える指摘である。

転記の書き方は移し先の reference に従い、本書の文をそのまま貼らない。
本書の文は差分または監査という文脈の中で書かれており、その文脈が消えた後には読めない。

**扱いの欄はリンクにしない。**
転記先の文書名と、その中での識別子（`issues.md` の ID、設計文書の保留の題、`terms.md` の語）で指す。
`issues.md` の項目は修正とともに消え、設計文書の保留は決まると決定済みへ移り、`terms.md` の語は改名でアンカーが変わるので、リンクは必ず切れる。
識別子で指しておけば、指した先が見つからないこと自体が、処理が済んだという情報になる。

転記先から本書へのリンクは張らない。
双方向にすると、片方が必ず腐る。
出所をたどりたいときは、`issues.md` の ID で `docs/reviews/` を検索すれば足りる。

## 書かないこと

**変更内容の要約**は書かない。
何が変わったかは git が正本であり、差分を日本語に書き直したものはレビューではない。
変更に触れるのは、指摘の根拠として必要なときに限る。

**修正コード**は書かない。
直し方は §4 の扱いに 1 文で書き、実装は `issues.md` の対応方針か実装計画書が持つ。

**設計判断の理由**は設計文書が持つ。
レビューで新しい設計判断が生まれたなら、それは指摘ではなく決定であり、設計文書に書いてから本書からは種別 設計論点 として指す。

**語の定義**は `terms.md` が持つ。
種別 用語 の指摘に正しい定義を書かず、`terms.md` をどう直すかだけを扱いに書く。

**書式の好み**は書かない。
formatter と linter が正本であり、それらが検出しないものだけを指摘に値するものとして扱う。

コードブロックを置いてよいのは、指摘の該当箇所を示す既存コードの引用に限る（行番号付きリンクを添える）。

## 根拠の出所

共通規範の §「根拠の出所を区別する」に従い、本書では §4 の根拠と確度でこれを形式化している。

3 分類との対応は次のとおりである。
コードで確認した事実が確度 高、コードから読み取った意図が確度 中、確認できていないことが確度 低 である。
恒久文書では書かないことにしている 3 つ目を、本書は確度を明示した上で書いてよい。

再現手順やコマンドで確かめたなら、そのコマンドを根拠に書く。
読んだだけなのか実行したのかで、指摘の重みが変わる。

## ライフサイクル

- レビューを実施した直後に書く
- 発行したら §1 から §5 を凍結する（§「不変性」）
- 指摘を転記する（§「転記」）
- 起票、修正、判断の訂正が起きたら §6 に追記する
- 削除しない

同じ範囲を再びレビューするときは、この文書を書き換えず、新しい日付の文書を作る。
前回の文書を §2.3 の観点か §5 で参照してよく、前回見た範囲を今回の観点から外したなら、その旨を §2.2 に書く。

## 執筆後の点検

共通規範の §「共通の執筆後の点検」に加えて、次を確認する。

1. §2.2 が空でないか。「なし」「特になし」だけで終わっていないか
2. §2.2 の各項目に、見なかった理由があるか
3. §2.3 に観点が列挙されているか
4. すべての指摘に、該当箇所、何が問題か、根拠、影響、扱いの 5 ラベルがあるか
5. すべての指摘に扱いがあり、転記先か転記しない理由が書かれているか。`rg -c '^\*\*扱い\*\*' docs/reviews/<slug>.md` が指摘の件数と一致すること
6. 一覧表の行と本体が 1 対 1 か。どちらか片方にしかない ID がないか
7. すべての指摘の種別が 4 つのいずれかで、扱いの転記先が §「転記」の表と対応しているか
8. 確度が根拠と食い合っているか。確度 高 の指摘に「思われる」「はず」「かもしれない」が混ざっていないか
9. §1.2 にレビュー日、レビューの型、対象コミット、レビュアーの 4 つがあるか
10. コードへの参照に行番号があるか。`rg -nH '\]\((\.\./)+[^)#]*\.[A-Za-z0-9]+\)' docs/reviews/*.md | rg -v '\.md\)'` が空であること（`#L` の欠けたコードへのリンクを拾い、文書どうしの `.md` リンクは除く）
11. 転記先の識別子がリンクになっていないか。`rg -n '\*\*扱い\*\*' -A 2 docs/reviews/<slug>.md` に `](` がないこと
12. 変更内容の要約や修正コードを貼っていないか。コードブロックが §「書かないこと」の 1 例外に収まっているか
13. §5 に、疑わずに読み流した箇所が混ざっていないか
14. §6 のすべての行に日付があるか
15. 発行済み文書を触ったなら、変更が §6 への追記と誤字修正に留まっているか。`git diff` で §1 から §5 に差分がないことを確認する

## 付録：観点の例

観点は、そのレビューで実際に探したものを書く。
次は例であり、そのまま貼らない。
探していない観点を書けば、§2.2 に書くべきものを §2.3 に隠したことになる。

差分レビューでよく立つ観点。

- 変更した関数の呼び出し元が、変更後の前提を満たしているか
- 追加した分岐に対応するテストがあるか
- 既存の不変条件（該当する設計文書の各論章）を崩していないか
- エラーを握り潰していないか
- 外部から見える契約（API、設定、保存形式）が変わっていないか

監査レビューでよく立つ観点。

- 層をまたぐ依存が設計どおりの向きか
- 同じ処理が複数箇所に複写されていないか
- 失敗経路で状態が中途半端に残らないか
- 並行実行で壊れる箇所がないか
- `terms.md` の識別子と実装の名前が食い違っていないか

観点は 3 つから 6 つに絞る。
10 個並べたレビューは、たいていそのうち何個かを実際には見ていない。
