# 実装計画書の記述規範

`docs/plans/<slug>.md` を書くとき、直すとき、点検するとき、畳むときは、以下の規範に従う。
`<slug>` は作業を指す kebab-case の短い名前にする。

この規範が守るのは 3 点である。
実装者（人間でも AI エージェントでもよい）が本書だけを読んで手を動かせること。
実装者以外が、終わったかどうかを判定できること。
計画書が消えても、そこで下した決定が失われないこと。

文体、図、情報密度、根拠の扱いは `../design-docs-writing/SKILL.md` と共有し、本書では実装計画書に固有の点だけを定める。
本書で設計文書群というときは、`docs/DESIGN.md` と、そこからリンクする `docs/design/*.md` を指す。
`docs/DESIGN.md` を入口として責務分担表をたどり、計画の関心事を受け持つ設計文書を特定する。

## 文書の責務

| 文書 | 受け持つもの | 寿命 |
| --- | --- | --- |
| `docs/DESIGN.md` と、そこからリンクする `docs/design/*.md` | なぜその形なのか。不変条件、採用理由、却下した案、未決の論点 | プロジェクトと同じ |
| `docs/ISSUES.md` | コードを読んで確認した明確な不具合 | 修正されるまで |
| `docs/plans/<slug>.md` | この作業で何をどの順に作り、どうなったら終わりか | 作業が終わるまで |

境界は寿命で判定し、作業が終わった後にも価値が残るものは計画書に書かない。

計画を立てる過程で新しい設計判断を下したときは、先にその関心事を受け持つ設計文書の設計判断章に書き、計画書には結論とリンクだけを置く。
横断的な判断は `docs/DESIGN.md`、1 つの関心事に閉じる判断は既存の詳細文書を正本とする。
対応する詳細文書がない場合は `docs/DESIGN.md` を正本とする。
計画書の作成や完了に便乗して設計文書を分割せず、分割が必要なら design-docs-writing の更新として別に扱う。
順序を逆にすると、計画書を消した時点で理由が消える。

## 計画書の粒度

1 つの計画書が扱うのは、1 度にレビューできる 1 まとまりの変更である。
手順が 10 を超えるなら作業が大きすぎるので、依存関係で切って分ける。

分けたときの `<slug>` は、通し番号ではなく、その計画書が何をするかで付ける。
`refactor-storage-1` と `refactor-storage-2` ではなく、`storage-facade-split` と `storage-driver-retry` にする。
番号で分けると、先に片方が完了して消えた時点で、残った番号が何の続きか読めなくなる。

計画書どうしの依存は、後続の側の §4.1 に書き、先行の側には書かない。
先行は、自分より後にできたものを知らないためである。

## 4 つのモード

**新規作成**：コードを読んで現状を確かめ、章立て（§「章立て」）を立てて各章を埋める。
確認できなかったことは本文に書かない（§「根拠の出所」）。
未決が残っている状態を完成としない。

**更新**：実装中に前提が崩れたときに、手順を書き換えてから続ける。
黙って計画から逸れない。
逸れた実装は、後から誰も検証できない。
一覧表の状態列を進めることは本文の書き換えに当たらず、この手続きを要さない。

**点検**：§「執筆後の点検」を機械的に走らせ、本文は変更せず所見と根拠だけを報告する。

**完了**：受け入れ検証が通った後に、残す価値のある内容を移してから計画書を削除する（§「計画書を畳む」）。
このモードだけは、成果物が計画書ではなく移し先の設計文書と `ISSUES.md` の差分である。

## 情報密度

design-docs-writing の §「情報密度」に従う。
保持する意味要素は次に置き換える。

- 目的と、完了したと判定する条件
- 非目標と、この作業で外した理由
- 現状のうち、変更の可否と手順に影響する事実
- 前提とする決定と、その正本へのリンク
- 各手順の変更箇所、やること、完了条件、依存
- 受け入れ検証の条件番号、コマンド、期待する結果
- 巻き戻せない変更と、その戻し方

次の記述は追加で削除または統合してよい。

- 手順の題を言い直しただけの「やること」
- コードを読めば分かる構造をなぞった現状の描写
- 採用しなかった案の検討経過（その判断を受け持つ設計文書の却下案に移す）

文字数の増加を禁じる規則は、圧縮を明示的に依頼されたときにだけ適用する。
更新モードで前提の変化を書き足せば文字数は増えるのが正常である。

## 検証用サブエージェント

design-docs-writing の §「検証用サブエージェント」に従い、`verifier` を必須とする範囲と blocking の一覧を次に置き換える。

新規作成では必須とし、利用できない場合は計画書を作らないで報告する。
更新では、章の追加や削除、完了条件の変更、手順の追加や削除、依存順の変更を伴うときだけ必須とする。
語句の言い直し、リンクの張り替え、状態列の更新だけなら要さない。
実装の途中で止まらないための例外であり、次に必須の書き換えをするときにまとめて検証する。
点検では本文を変更しないため要さない。
完了では、移し先の設計文書と `ISSUES.md` の変更に design-docs-writing の必須範囲が適用される。

blocking とする指摘は次に置き換える。

- 完了条件が観測可能でない
- §2.1 の条件と §6 の行が 1 対 1 に対応していない
- 手順に変更する箇所または完了条件がない
- 依存順が実行不能である（先行手順の結果に依存しているのに順序が逆）
- 現状の記述がコードと食い違う
- 設計判断の理由が本文にあり、正本となる設計文書にない
- 設計判断、不変条件、保留の正本が設計文書群の責務分担と一致しない
- 未決が残っている
- 見出し、アンカー、リンクの破損
- 圧縮を依頼されたときの、圧縮後の文字数増加

## 章立て

```
1. この計画について
   1.1 文書間の責務分担
   1.2 作成日と対象コミット
2. 目的と完了条件
   2.1 完了条件
   2.2 非目標
3. 現状
4. 変更方針
   4.1 前提とする決定
   4.2 影響範囲
5. 手順
6. 受け入れ検証
7. リスクと巻き戻し
```

1 章から 6 章は必須である。
7 章は `git revert` で元に戻らない変更を含むときだけ置き、含まないなら見出しごと置かない。
見出しには `## 1.` `### 1.1` の形で番号を振り、`####` には振らない。

### 1. この計画について

この作業が何かを 1 文から 2 文で述べる。

**1.1 文書間の責務分担**は表で書き、`本書`、`DESIGN.md`、`[ISSUES.md](../ISSUES.md)` の分担を列挙する。
設計文書が分割されている場合は、この計画に関係する詳細文書も実体への相対リンク付きで列挙し、それぞれが受け持つ範囲を書く。
設計文書へのリンクは計画が前提とする見出しのアンカーまで含める。
たとえば全体構成は `[DESIGN.md](../DESIGN.md#3-全体構成)`、storage の境界は `[storage.md](../design/storage.md#2-責務と境界)` と書く。
自己参照は `本書` とだけ書き、ファイル名や自己リンクを併記しない。

**1.2 作成日と対象コミット**は必須である。
手順は現状のコードを前提に書かれており、いつ時点かが分からないと読めない。

### 2. 目的と完了条件

目的は、利用者や運用から見て何が変わるかで書き、実装の言い換えにしない。
「キャッシュ層を入れる」は実装であり、「一覧取得が 1000 件で 200 ms 以内に返る」が目的である。

**2.1 完了条件**は、実装者以外が真偽を判定できる、到達すべき観測可能な状態で書く。
確かめ方は本節に書かず、実行するコマンドと期待する結果は §6 が持つ。
条件は番号付きで列挙し、§6 の行と 1 対 1 で対応させる。

次は実装の言い換えであり、判定できないので完了条件ではない。

- 「〜を実装する」
- 「〜が動くこと」
- 「〜をリファクタリングする」

すべて満たされたときに作業を完了とする。
書き換え方は §「付録：完了条件の書き換え例」を見る。

**2.2 非目標**には、この作業ではやらないと決めたものを列挙する。
`docs/DESIGN.md` のスコープ外と混同しない。
スコープ外は恒久的に作らない決定であり、非目標はこの作業でやらないだけである。
将来必要になるものは、該当する設計文書の保留か `ISSUES.md` に移してからリンクする。
非目標に置いたまま計画書を消すと、誰も拾わない。

### 3. 現状

変更に関わる範囲のコードが、いまどうなっているかを、コードで確認した事実だけで書く。
描写は変更に影響する範囲に限り、コードを読めば分かる構造はなぞらず行番号付きリンクで指す。
そのうえで、なぜ現状では足りないのかを 1 文で書く。
この 1 文がないと、手順が必要かどうかを読み手が判断できない。

### 4. 変更方針

どういう形に変えるかを、手順に分ける前にまとめて書く。
全体像を先に置かないと、個々の手順の意図が読めない。

**4.1 前提とする決定**は表で書き、列は決定と正本へのリンクの 2 つとする。
理由はリンク先にあるため書かない。
正本となる設計文書にない決定があるなら、先にその文書へ足してから本表に載せる。

計画書を分割したとき（§「計画書の粒度」）は、先行する計画書の完了も前提であり、本表に載せる。
決定の列に「`<先行の slug>` が完了していること」、リンクの列にその計画書への相対リンクを書く。
先行が完了して削除されたら、この行も消す。

**4.2 影響範囲**には、触るコンポーネントと、触らないが影響を受けるものを書く。
外部から見える変更（API、設定ファイル、保存形式）があれば明記し、互換性が壊れるかどうかを 1 文で書く。

### 5. 手順

冒頭に一覧表を置く。
列は番号、内容、依存、状態の 4 つで、番号は項目へのアンカーリンクにする。
状態は `未着手`、`進行中`、`完了` の 3 つとする。

**進捗はこの表にだけ書く。**
各手順の本体にも、ほかの章にも状態を書かない。
2 箇所に書くと必ず片方が腐る。

各手順は次の型で書く。

```markdown
<a id="s-1"></a>
### 手順 1. 何をするかが分かる短い題

**変更する箇所**
既存ファイルは行番号付きリンク。新規ファイルはパスと役割。

**やること**
何をどう変えるか。題の言い直しにしない。

**完了条件**
この手順が終わったと判定できる観測可能な事象。
```

3 節すべてを書く。
`<a id="s-1"></a>` の明示アンカーを置く。
日本語見出しの自動アンカーは長く、題を直すと壊れるためである。

手順は依存順に並べる。
順序を入れ替えても成立する手順は、一覧表の依存列を空にする。
依存列が埋まっている手順は、依存先が完了するまで着手できない。

番号は識別子であり、通し番号ではない。
更新で手順が不要になったら、一覧表の行と本体を削除し、後続の番号を詰めない。
振り直すと `s-N` のアンカーと依存列の参照がすべてずれる。
手順を足すときは未使用の最大番号の次を取り、並びだけを依存順に保って挿入する。

各手順は、それ単体でビルドと既存テストが通る単位にする。
通らない中間状態をまたぐ手順は、そう明記する。

### 6. 受け入れ検証

§2.1 の各条件を、それが真だと確かめる手続きに落とす。

表で書き、列は §2.1 の条件番号、実行するコマンド、期待する結果の 3 つとする。
§2.1 のすべての条件が 1 行以上に現れる。
対応する行を書けない条件はそもそも判定できない条件であり、§2.1 に戻って書き直す。
条件の文言は再掲せず、番号で指す。

手順の完了条件がその段階の終わりを見るのに対して、本章は作業全体が要求を満たしたかを見る。

コマンドはコピーして実行できる形で書き、期待する結果の列を空にしない。
結果のないコマンドは検証にならない。

新しく足すテストがあるなら、何を守るテストかを 1 行で書く。
テストのコードは書かない。

### 7. リスクと巻き戻し

元に戻らない変更とは、データマイグレーション、公開済み API の変更、データの削除、外部サービスへの反映である。

各項目に、失敗したときに何が起きるかと、戻す手順を書く。
戻せないものは戻せないと書く。
戻せないと分かっていることと、戻せると思い込んでいることは違う。

## 書かないこと

**設計判断の理由**は、その判断を受け持つ設計文書が持つ（§「文書の責務」）。
**確認済みの不具合の詳細**は `ISSUES.md` が持ち、関連するものは ID で参照する。
**セットアップ手順と依存パッケージ**は `README.md` が持つ。

**完成コード**は書かない。
関数の本体、実装の疑似コード、差分の貼り付けは、実装時に必ずずれる。
計画書がコードの下書きになると、同じものを 2 箇所で保守することになる。

コードブロックを置いてよいのは次の 2 つに限る。

1. 現状を示す既存コードの引用（行番号付きリンクを添える）
2. 新しく決める型やインターフェースのシグネチャ（それ自体が契約であるため）

## 根拠の出所

design-docs-writing の §「根拠の出所を区別する」に従い、本書では特に現状章と完了条件で厳密に守る。
確認していない現状を断定で書くと、その上に積んだ手順がすべて崩れる。

確認できていない前提が手順に必要なときは、確認そのものを手順 1 に置く。
調べることを手順にしてよく、その完了条件は何が分かったかで書く。

## ライフサイクル

- 着手前に書き、合意を得てから実装に入る
- 実装中に前提が崩れたら、手順を書き換えてから続ける（§「4 つのモード」）
- 新しい設計判断は正本となる設計文書に、積み残した不具合は `ISSUES.md` に移してからリンクする
- 受け入れ検証が通ったら、§「計画書を畳む」に従って畳む

完了した計画書を残さない。
実装済みの計画はコードと git の履歴が正であり、残った文書は必ずコードと食い違う。

## 計画書を畳む

§6 の受け入れ検証がすべて通り、一覧表の状態列がすべて `完了` になった時点で畳む。
1 つでも未達なら畳まない。
未達のまま終わらせるなら、それはやらないと決めたということであり、先に §2.2 の非目標へ移して外した理由を書く。

畳む作業は、移す、確かめる、消すの 3 段である。
消すのを先にしない。
消した後では、何を移し損ねたかを誰も知り得ない。

**移す**では、本文を上から 1 章ずつ見て、寿命が作業より長いものだけを次の対応で移す。

| 計画書にあるもの | 移し先 |
| --- | --- |
| 実装の過程で下した設計判断とその理由 | その判断を受け持つ設計文書の設計判断章の決定済み |
| 検討して退けた案 | 同じ決定の却下案 |
| 決めきれず先送りにした論点 | その論点を受け持つ設計文書の設計判断章の保留（決める条件を必ず付ける） |
| 実装して分かった不変条件と、それが崩れる条件 | その関心事を受け持つ設計文書の該当する各論章 |
| 積み残した不具合 | `ISSUES.md` に 1 項目として起票 |
| 非目標のうち、いずれ必要になるもの | 該当する設計文書の保留か `ISSUES.md` |
| 非目標のうち、恒久的に作らないと決めたもの | `DESIGN.md` のスコープ外 |
| 恒久的に回したい受け入れ検証 | テストか CI の設定。文書には移さない |

現状、影響範囲、手順、リスクと巻き戻しは、コードと git の履歴が正であり、通常は移すものがない。
移すものがないと確かめたうえで、何もしない。

移し先の書き方は design-docs-writing に従い、計画書の文をそのまま貼らない。
計画書の文は手順という文脈の中で書かれており、その文脈が消えた後には読めない。

**確かめる**では、計画書を閉じたまま移し先だけを読み、内容が通じるかを見る。
移した決定が、手順番号や `<slug>` を指していないこと。
起票した項目が、design-docs-writing の §「1 項目の型」の 5 節を満たしていること。
計画書へのリンクがどこにも残っていないこと。
最後の 1 つは `rg -n '<slug>' --glob '!docs/plans/**' .` が空であることで確かめる。

**消す**では、`git rm docs/plans/<slug>.md` で削除し、移し先の変更と同じコミットに含める。
コミットを分けると、片方だけが取り込まれたときに内容が失われる。

## 参照とリンク

本書は作成日と対象コミットを明記したスナップショットであり、腐ることが前提である。
そのためコードへの参照は `ISSUES.md` と同じ扱いにし、行番号付きリンク（`#L42`）を使う。
設計文書を指すときは、対象ファイルと見出しのアンカーまで含める。

文体と表記は design-docs-writing の §「文体と表記」に、図は §「図」に従う。

## 執筆後の点検

書き終えたら次を確認し、機械化できる項目はコマンドで検査する。
畳むときの確認は §「計画書を畳む」に定める。

1. §2.1 と各手順の完了条件が観測可能か。「実装する」「動くこと」「対応する」で終わる条件が残っていないか
2. §2.1 の条件が番号付きで、§6 の行と 1 対 1 か。どちらか片方にしかない条件がないか
3. すべての手順に、変更する箇所、やること、完了条件の 3 節があるか
4. 進捗が一覧表の状態列だけにあるか。`rg -n '完了した|完了済み|実装済み|対応済み|着手済み|残りは' docs/plans/*.md` が空であること（節名の「完了条件」を拾わないよう、進捗を述べる表現だけを検索する）
5. 未決が残っていないか。「未定」「検討する」「どちらか」で検索する
6. 設計判断の理由が本文になく、理由を述べている箇所が責務分担に一致する正本の設計文書へのリンクになり、§1.1 と §4.1 の設計文書リンクが対象ファイルと見出しアンカーを含んでいるか
7. 非目標が書かれ、そのうち将来必要なものが該当する設計文書か `ISSUES.md` に移されているか
8. 作成日と対象コミットがあるか
9. コードへの参照に行番号があるか。`rg -nH '\]\((\.\./)+[^)#]*\.[A-Za-z0-9]+\)' docs/plans/*.md | rg -v '\.md\)'` が空であること（`#L` の欠けたコードへのリンクを拾い、文書どうしの `.md` リンクは除く）
10. 関数本体や疑似コードを貼っていないか。コードブロックが §「書かないこと」の 2 例外に収まっているか
11. 手順が 10 を超えていないか。超えるなら §「計画書の粒度」に従って分ける
12. 手順番号が振り直されていないか。依存列が指す番号と本文の `s-N` アンカーがすべて実在するか

14. 巻き戻せない変更があるのに 7 章がないか。逆に、7 章があるのに戻せない変更がないか
15. §6 の期待する結果の列に空欄がないか

## 付録：完了条件の書き換え例

左は実装の言い換えで判定できず、右は実装者以外が真偽を確かめられる。

| 判定できない書き方 | 観測可能な完了条件 |
| --- | --- |
| キャッシュを実装する | 1000 件での一覧取得の p95 が 200 ms 未満 |
| エラーハンドリングを直す | 存在しない ID への `GET /items/{id}` が 404 と `{"code":"not_found"}` を返す |
| 設定を読めるようにする | `config.toml` の `port = 9000` が起動時に反映され、9000 で listen する |
| テストを追加する | `rename` 失敗時の分岐がテストで覆われ、既存テストが全件通る |
| リファクタリングする | `src/storage/facade.rs` が `driver::` を直接参照せず、既存テストが全件通る |

右の列に共通するのは、対象と、それが満たすべき値や状態の 2 つが特定されている点である。
どちらかが欠けた条件は、書き直す。

確かめる手続きは完了条件そのものには書かず、§6 の表に条件番号と期待する結果とともに置く。
上から順に `cargo bench items_list`、`cargo test api::not_found`、`ss -ltn`、`cargo test storage::`、`rg 'driver::' src/storage/facade.rs` が対応する。
