# 実装計画書の記述規範

`docs/plans/<slug>.md` を書くとき、直すとき、点検するときは、以下の規範に従う。
`<slug>` は作業を指す kebab-case の短い名前にする。

この規範が守ろうとしているのは 3 点である。
第一に、実装者（人間でも AI エージェントでもよい）が本書だけを読んで手を動かせること。
第二に、実装者以外が、終わったかどうかを判定できること。
第三に、計画書が消えても、そこで下した決定が失われないこと。

文体、図、情報密度、根拠の扱いは `../design-docs-writing/SKILL.md` と共有する。
本書では実装計画書に固有の点だけを定め、共有部分は該当節を参照する。

## 文書の責務

| 文書 | 受け持つもの | 寿命 |
| --- | --- | --- |
| `docs/DESIGN.md` | なぜその形なのか。不変条件、採用理由、却下した案、未決の論点 | プロジェクトと同じ |
| `docs/ISSUES.md` | コードを読んで確認した明確な不具合 | 修正されるまで |
| `docs/plans/<slug>.md` | この作業で何をどの順に作り、どうなったら終わりか | 作業が終わるまで |

境界は寿命で判定する。
作業が終わった後にも価値が残るものは、計画書に書かない。

計画を立てる過程で新しい設計判断を下したときは、先に `DESIGN.md` の設計判断章に書き、計画書には結論とリンクだけを置く。
順序を逆にすると、計画書を消した時点で理由が消える。

## 計画書の粒度

1 つの計画書が扱うのは、1 度にレビューできる 1 まとまりの変更である。
手順が 10 を超えるなら、作業が大きすぎる。
依存関係で切って計画書を分ける。

## 3 つのモード

**新規作成**：コードを読んで現状を確かめ、章立て（§「章立て」）を立て、各章を埋める。
確認できなかったことは本文に書かない（§「根拠の出所」）。
未決が残っている状態を完成としない。

**更新**：実装中に前提が崩れたときに、手順を書き換えてから続ける。
黙って計画から逸れない。
逸れた実装は、後から誰も検証できない。
手順の一覧表の状態列を進めることは本文の書き換えに当たらず、この手続きを要さない。

**点検**：§「執筆後の点検」のチェックリストを機械的に走らせる。
本文は変更せず、所見と根拠だけを報告する。

## 情報密度

design-docs-writing の §「情報密度」に従う。
保持する意味要素は次に置き換える。

- 目的と、完了したと判定する条件
- 非目標と、この作業で外した理由
- 現状のうち、変更の可否と手順に影響する事実
- 前提とする決定と、その正本へのリンク
- 各手順の変更箇所、やること、完了条件、依存
- 受け入れ検証のコマンドと期待する結果
- 巻き戻せない変更と、その戻し方

次の記述は追加で削除または統合してよい。

- 手順の題を言い直しただけの「やること」
- コードを読めば分かる構造をなぞった現状の描写
- 採用しなかった案の検討経過（`DESIGN.md` の却下案に移す）

## 検証用サブエージェント

design-docs-writing の §「検証用サブエージェント」に従う。
blocking とする指摘は次に置き換える。

- 完了条件が観測可能でない
- 手順に変更する箇所または完了条件がない
- 依存順が実行不能である（先行手順の結果に依存しているのに順序が逆）
- 現状の記述がコードと食い違う
- 設計判断の理由が本文にあり、`DESIGN.md` にない
- 未決が残っている
- 見出し、アンカー、リンクの破損
- 圧縮後の文字数増加

## 章立て

```
1. この計画について
   1.1 文書間の責務分担
   1.2 作成日と対象コミット
2. 目的と完了条件
   2.1 完了条件
   2.2 非目標
3. 現状
4. 変更方針
   4.1 前提とする決定
   4.2 影響範囲
5. 手順
6. 受け入れ検証
7. リスクと巻き戻し
```

1 章から 6 章は必須である。
7 章は `git revert` で元に戻らない変更を含むときだけ置く。
含まないなら見出しごと置かない。

見出しには `## 1.` `### 1.1` の形で番号を振る。
`####` には番号を振らない。

### 1. この計画について

この作業が何かを 1 文から 2 文で述べる。

**1.1 文書間の責務分担**は表で書く。
`本書`、`[DESIGN.md](../DESIGN.md)`、`[ISSUES.md](../ISSUES.md)` の分担を列挙する。
自己参照は `本書` とだけ書き、ファイル名や自己リンクを併記しない。

**1.2 作成日と対象コミット**は必須である。
計画は現状のコードを前提に書かれており、いつ時点かが分からないと手順が読めない。

### 2. 目的と完了条件

目的は、利用者や運用から見て何が変わるかで書く。
実装の言い換えにしない。
「キャッシュ層を入れる」は実装であり、「一覧取得が 1000 件で 200 ms 以内に返る」が目的である。

**2.1 完了条件**は、実装者以外が実行して真偽を判定できる形で書く。
コマンドと期待する結果、または到達すべき観測可能な状態で書く。

次は完了条件ではない。
どれも実装の言い換えであり、判定できない。

- 「〜を実装する」
- 「〜が動くこと」
- 「〜をリファクタリングする」

条件は箇条書きで列挙する。
すべて満たされたときに作業を完了とする。
書き換え方は §「付録：完了条件の書き換え例」を見る。

**2.2 非目標**には、この作業ではやらないと決めたものを列挙する。
`DESIGN.md` のスコープ外と混同しない。
スコープ外は恒久的に作らない決定であり、非目標はこの作業でやらないだけである。
将来必要になるものは、`DESIGN.md` の保留か `ISSUES.md` に移してからリンクする。
非目標に置いたまま計画書を消すと、誰も拾わない。

### 3. 現状

変更に関わる範囲のコードが、いまどうなっているかを書く。
書くのはコードで確認した事実だけである。

そのうえで、なぜ現状では足りないのかを 1 文で書く。
この 1 文がないと、手順が必要かどうかを読み手が判断できない。

描写は変更に影響する範囲に限る。
コードを読めば分かる構造をなぞらず、行番号付きリンクで指す。

### 4. 変更方針

どういう形に変えるかを、手順に分ける前にまとめて書く。
全体像を先に置かないと、個々の手順の意図が読めない。

**4.1 前提とする決定**は表で書く。
列は、決定と正本へのリンクの 2 つ。
理由は書かない。
リンク先にある。
本書を書く時点で `DESIGN.md` にない決定があるなら、先に `DESIGN.md` に足してから本表に載せる。

**4.2 影響範囲**には、触るコンポーネントと、触らないが影響を受けるものを書く。
外部から見える変更（API、設定ファイル、保存形式）があれば明記する。
互換性が壊れるかどうかを 1 文で書く。

### 5. 手順

冒頭に一覧表を置く。
列は、番号、内容、依存、状態の 4 つ。
番号は項目へのアンカーリンクにする。
状態は `未着手`、`進行中`、`完了` の 3 つとする。

**進捗はこの表にだけ書く。**
各手順の本体にも、ほかの章にも、状態を書かない。
2 箇所に書くと必ず片方が腐る。

各手順は次の型で書く。

```markdown
<a id="s-1"></a>
### 手順 1. 何をするかが分かる短い題

**変更する箇所**
既存ファイルは行番号付きリンク。新規ファイルはパスと役割。

**やること**
何をどう変えるか。題の言い直しにしない。

**完了条件**
この手順が終わったと判定できる観測可能な事象。
```

3 節すべてを書く。
`<a id="s-1"></a>` の明示アンカーを置く。
日本語見出しの自動アンカーは長く、題を直すと壊れるためである。

手順は依存順に並べる。
順序を入れ替えても成立する手順は、一覧表の依存列を空にする。
依存列が埋まっている手順は、依存先が完了するまで着手できない。

各手順は、それ単体でビルドと既存テストが通る単位にする。
通らない中間状態をまたぐ手順は、そう明記する。

### 6. 受け入れ検証

§2.1 の完了条件を、実行するコマンドと期待する結果に落とす。

手順ごとの完了条件との違いは対象である。
手順の完了条件はその段階が終わったかを見る。
本章は作業全体が要求を満たしたかを見る。

コマンドはコピーして実行できる形で書く。
期待する結果を各コマンドに添える。
結果を書かないコマンドは検証にならない。

新しく足すテストがあるなら、何を守るテストかを 1 行で書く。
テストのコードは書かない。

### 7. リスクと巻き戻し

`git revert` で元に戻らない変更を含むときだけ置く。
データマイグレーション、公開済み API の変更、データの削除、外部サービスへの反映が該当する。

各項目に、失敗したときに何が起きるかと、戻す手順を書く。
戻せないものは戻せないと書く。
戻せないと分かっていることと、戻せると思い込んでいることは違う。

## 書かないこと

**設計判断の理由**は `DESIGN.md` が持つ。
本文には結論と、`DESIGN.md` の該当節へのリンクだけを置く。

**確認済みの不具合の詳細**は `ISSUES.md` が持つ。
関連するものは ID で参照する。

**セットアップ手順と依存パッケージ**は `README.md` が持つ。

**完成コード**は書かない。
関数の本体、実装の疑似コード、差分の貼り付けは、実装時に必ずずれる。
計画書がコードの下書きになると、同じものを 2 箇所で保守することになる。

コードブロックを置いてよいのは次の 2 つに限る。

1. 現状を示す既存コードの引用（行番号付きリンクを添える）
2. 新しく決める型やインターフェースのシグネチャ（それ自体が契約であるため）

## 根拠の出所

design-docs-writing の §「根拠の出所を区別する」に従う。
本書では特に現状章と完了条件で厳密に守る。
確認していない現状を断定で書くと、その上に積んだ手順がすべて崩れる。

確認できていない前提が手順に必要なときは、確認そのものを手順 1 に置く。
調べることを手順にしてよい。
その完了条件は、何が分かったかで書く。

## ライフサイクル

- 着手前に書き、合意を得てから実装に入る
- 実装中に前提が崩れたら、手順を書き換えてから続ける
- 新しい設計判断は `DESIGN.md` に移してからリンクする
- 積み残した不具合は `ISSUES.md` に起票してからリンクする
- 完了したら、計画書を削除する

完了した計画書を残さない。
実装済みの計画はコードと git の履歴が正であり、残った文書は必ずコードと食い違う。
残す価値のあるものは、削除する前に `DESIGN.md` か `ISSUES.md` に移す。

## 参照とリンク

本書は作成日と対象コミットを明記したスナップショットであり、腐ることが前提である。
そのためコードへの参照は `ISSUES.md` と同じ扱いにし、行番号付きリンク（`#L42`）を使う。
`DESIGN.md` を指すときは見出しのアンカーまで含める。
自己参照は `本書` とだけ書く。

文体と表記は design-docs-writing の §「文体と表記」に、図は §「図」に従う。

## 執筆後の点検

書き終えたら次を確認する。
機械化できる項目はコマンドで検査する。

1. §2.1 と各手順の完了条件が観測可能か。「実装する」「動くこと」「対応する」で終わる条件が残っていないか
2. すべての手順に、変更する箇所、やること、完了条件の 3 節があるか
3. 進捗が手順の一覧表の状態列だけにあるか。本文に「完了」「済み」が漏れていないか
4. 未決が残っていないか。「未定」「検討する」「どちらか」で検索する
5. 設計判断の理由が本文に書かれていないか。理由を述べている箇所が `DESIGN.md` へのリンクになっているか
6. 非目標が書かれ、そのうち将来必要なものが `DESIGN.md` か `ISSUES.md` に移されているか
7. 作成日と対象コミットがあるか
8. コードへの参照に行番号があるか。`rg -n '\]\(\.\./\.\./[^)#]*\.[a-z]+\)' docs/plans/` が空であること（拡張子付きのファイルリンクで `#L` が欠けたものを拾う）
9. 関数本体や疑似コードを貼っていないか。コードブロックが §「書かないこと」の 2 例外に収まっているか
10. 手順が 10 を超えていないか。超えるなら計画書を分ける
11. 巻き戻せない変更があるのに 7 章がないか。逆に、7 章があるのに戻せない変更がないか
12. 受け入れ検証のすべてのコマンドに期待する結果が添えてあるか
13. 一文一行になっているか。節参照が `§` 付きか。地の文と見出しにダッシュがないか。`rg '[—―]' docs/plans/*.md` を確認する
14. 新規作成と更新では `verifier` が `pass` し、その後にメインエージェントが差分と必須検査を再確認したか

## 付録：完了条件の書き換え例

左は実装の言い換えであり、判定できない。
右は実装者以外が実行して真偽を確かめられる。

| 判定できない書き方 | 観測可能な完了条件 |
| --- | --- |
| キャッシュを実装する | `cargo bench items_list` の p95 が 200 ms 未満（1000 件） |
| エラーハンドリングを直す | 存在しない ID への `GET /items/{id}` が 404 と `{"code":"not_found"}` を返し、`cargo test api::not_found` が通る |
| 設定を読めるようにする | `config.toml` に `port = 9000` を書いて起動すると 9000 で listen し、`ss -ltn` に現れる |
| テストを追加する | `cargo test storage::` が通り、`rename` 失敗時の分岐がテストに含まれる |
| リファクタリングする | 既存テストが全件通り、`rg 'driver::' src/storage/facade.rs` が 0 件 |

右の列に共通するのは、実行するものと、期待する結果の 2 つが揃っている点である。
どちらかが欠けた条件は、書き直す。
