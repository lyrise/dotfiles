# Research Before Build

既存資産を先に調査し、実装前の採用判断と最小MVPを根拠付きで提案する。
調査結果を提示したら、ユーザーの承認を待って停止する。

## 守る境界

- 初回は読取調査だけを行う。コード、設定、設計文書、Issue、コメントなどを作成・変更しない。
- 候補をcloneせず、依存関係を導入せず、ビルドや第三者コードを実行しない。
- 実行検証や商用SaaSとの比較は、ユーザーが明示的に求めた場合だけ別工程として扱う。
- ネットワークやGitHub情報へアクセスできない場合は、記憶で補わず制約を報告する。
- リポジトリのライセンス適合性について法的判断を断定しない。ライセンス欠落や不明点を採用上のリスクとして示す。

## 1. 目的と制約を固める

1. ワークスペース、既存コード、ユーザーの説明から次を抽出する。
   - 解決したい問題と主要利用者
   - 必須機能と、あれば望ましい機能
   - 実行環境、技術スタック、導入・運用条件
   - ライセンス、セキュリティ、データ配置などの制約
2. 環境から確認できる事実は質問せず調べる。
3. 結論を左右する制約だけが不明な場合は、推奨案を添えて一度に一つずつ確認する。
4. 調査条件を短く明示してから探索を始める。

## 2. 候補を探索する

1. 問題名だけでなく、主要機能、同義語、関連カテゴリ、技術制約を組み合わせて複数の検索語を作る。
2. GitHub connectorまたはGitHub APIを利用できる場合は優先し、発見にはWeb検索も使う。
3. 検索結果やまとめ記事は候補発見にだけ使い、評価はリポジトリ、リリース、Issue、PR、公式ドキュメントなどの一次情報で裏付ける。
4. 無関係なテンプレート、ミラー、放置されたfork、実体のないサンプルを除外する。forkが有力ならupstreamとの関係も確認する。
5. 有力候補を3〜5件に絞る。基準を満たす候補が少なければ、件数を埋めず理由を述べる。

## 3. 同じ観点で評価する

各候補について、次を確認する。

- **適合性**: 必須機能の充足、主要な不足、想定利用者や用途の一致。
- **再利用性**: そのまま使える機能、API・CLI・プラグインなどの拡張点、分離可能なモジュール、必要な改変範囲。
- **保守状況**: archived状態、最終コミット、最終リリース、リリース周期、Issue・PRへの応答、主要貢献者の偏り。
- **品質の兆候**: テスト、CI、ドキュメント、移行手順、セキュリティポリシーや公開アドバイザリ。
- **導入と運用**: 公式の導入手順、Docker等の配布形態、必須サービス、データストア、認証、マイグレーション、プラットフォーム制約。
- **ライセンスとリスク**: ライセンス、採用を妨げる条件、重大な未解決問題、依存先や運用上の懸念。

Star数は発見や利用規模の補助情報としてのみ扱う。
更新間隔はプロジェクトの成熟度と過去の周期を踏まえて判断し、古いという理由だけで非保守と断定しない。
botによる依存更新だけを活発な開発の証拠にしない。

## 4. 証拠を区別する

- **確認済み**: GitHubの状態、履歴、ファイルなどを今回直接確認した事実。
- **文書記載**: READMEや公式ドキュメントが主張しているが、実行していない内容。
- **推定**: 構成や公開情報から導いた判断。

すべての時点依存情報に調査日を付け、主張の近くに直接参照できるリンクを置く。
読取調査を、インストール・ビルド・起動まで検証したかのように表現しない。

## 5. 採用方針を決める

必ず次のいずれか一つを推奨する。

- **そのまま使う**: 必須要件を満たし、追加実装より設定や運用整備が中心になる。
- **既存プロジェクトを基に改変する**: 中核機能を再利用でき、差分が拡張点または限定された変更として管理できる。
- **自分で開発する**: 適合性、ライセンス、保守性、安全性、統合コストのいずれかが致命的で、再利用の利益がない。

候補ごとの長短を並べるだけで終えず、推奨理由と棄却理由を要件に結び付ける。
不確実性が結論を左右する場合は、実装前に行う最小の追加検証を示す。

## 6. 最小MVPを提案する

次を具体化する。

- 採用する基盤または自作する最小部分
- MVPに含める主要フローと機能
- MVPから明示的に外す機能
- 最小の実行・配布構成
- 利用者から観測できる受け入れ条件
- 最初に検証する最大の技術リスク

## 出力形式

依頼者の言語で、次の順に簡潔にまとめる。

1. **推奨結論** — 三択の結論と一段落の要約
2. **候補比較表** — 候補、適合・再利用、保守状況、導入負荷、ライセンス、主要リスク
3. **判断理由** — 採用候補と棄却候補を要件に照らして説明
4. **最小MVP** — 基盤、対象機能、非対象、構成、受け入れ条件、先行検証
5. **未検証事項** — 文書記載や推定、追加確認が必要な事項
6. **承認待ち** — コードには着手していないことを明記し、方針の確認を求めて停止
