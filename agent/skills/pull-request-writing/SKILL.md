# Pull Request の規範

1 つの PR で 1 つの判断だけを求め、根拠を判断に必要な場所へ置き、検証を再現できる形で残す。
文体、表記、情報密度は `../design-docs-writing/SKILL.md` に従う。

## 変更を切り分ける

次のいずれかに当たる変更は、別の PR に分ける。

1. 片方だけ差し戻す可能性がある
2. レビューに必要な観点が異なる
3. 既存不具合の修正と新しい変更が混在する

ファイル数ではなく目的で判定する。
片方だけをマージすると壊れる場合に限り、複数の目的を同じ PR に含める。
実装前と PR 作成前に判定し、分割が必要なら履歴を組み替える前に切り方、順序、依存関係を提示して確認を得る。

## 根拠を置く場所

| 場所 | 書く内容 |
| --- | --- |
| コード内コメント | コードと同じ寿命を持つ実装意図 |
| 行指定コメント | その行でしか意味を持たない根拠 |
| PR 本文 | 背景、変更の構造と判断、影響、検証、レビュー観点 |
| コミットメッセージ | そのコミットをその順序で入れる理由 |
| `docs/DESIGN.md` | 恒久的な設計判断、不変条件、却下した案 |
| `docs/ISSUES.md` | コードから確認したスコープ外の不具合 |

同じ根拠を複数の場所に書かない。
`docs/DESIGN.md` がある場合は恒久的な判断をそこへ書き、PR の `変更内容` には要点と該当見出しへのリンクを置く。
`docs/DESIGN.md` がない場合は、PR 本文だけで判断を再構成できるように書く。

作業中に見つけた別目的の問題は同じ PR で直さない。
`docs/ISSUES.md` があれば同文書の規範に従って記録し、PR の `背景` から ID で指す。
記録先がなければ、扱わない理由と発見箇所を `背景` に書く。
関係する外部 Issue がある場合は `関連` に置く。

## コミットを構成する

コミットは依存順に並べ、各コミット単体でビルドとテストが通る状態にする。
テスト、ベンチマーク、計測コード、CI 設定など検証の土台を変えるコミットは、それを使う変更より先に置く。
コミットメッセージには変更理由を書き、数値を主張する場合はそのコミット単体の実測値も書く。

依存される PR を先に作る。
依存する PR は、依存先のブランチを base にして Draft で作る。

```bash
gh pr create --draft --base feat/dependency --title '...' --body-file pr-body.md
```

依存先がマージされたら、依存する PR の base を既定ブランチへ戻す。

```bash
gh pr edit <number> --base main
```

base の組み替えは Draft の間に行う。
ready の PR で組み替えが必要になった場合は、先に Draft へ戻す。

## PR 本文を書く

次の雛形を正本とする。
最初の 6 章は必ずこの順序で置き、`関連` は該当する項目がある場合だけ末尾に置く。

```markdown
## 背景

[この変更に必要な経緯、目的、目的としないことなどを書く。]

## 概要

[採用した手段を 1 文から 3 文で書く。]

## 変更内容

[変更と技術判断の理由を関心事ごとに書く。必要なら h3 を使う。]

## 影響範囲

[マージによって影響を受ける利用者、契約、運用などを書く。]

## 検証

- [x] `[実行したコマンド]`：結果
- [ ] 未検証：[対象と理由または残作業]

## レビュー観点

- [確認してほしい場所と判断内容]

## 関連

- [依存 PR または Issue と、この PR との関係]
```

### 背景

経緯、目的、目的としないこと、未対応事項などから、変更を判断するために必要な内容を書く。
Issue や議論へのリンクだけで済ませず、リンクを開かなくても必要性が分かるようにする。

### 概要

何をしたかを 1 文から 3 文で書く。
背景を繰り返さず、採用した手段だけを書く。

### 変更内容

変更と技術判断の理由を、機能、責務、データフローなどの関心事ごとに書く。
選ばなかった案が判断に重要なら、その案と採用しなかった理由も書く。
複数の関心事を分ける必要がある場合だけ h3 を使う。
ファイルごとの変更一覧にはしない。

### 影響範囲

挙動が変わる利用者、後方互換性、外部から見える契約、運用への影響を書く。
外部から見える契約には API、設定、保存形式、CLI 引数を含む。
影響がないと判断した項目は、確認した範囲と根拠を書く。
確認していない項目は保証せず、`検証` に未検証として書く。

### 検証

実施済みの検証は `- [x]`、未検証は `- [ ]` で書く。
実施済みの項目には、実行したコマンドまたは手順と結果を書く。
未検証の項目には、対象と理由または残作業を書く。
自動テスト、手動確認、測定結果を同じ章に置き、手動確認は再現できる手順にする。

### レビュー観点

確認してほしい場所と、そこで判断してほしい内容を具体的に書く。
「全体的に問題ないか」のような観点は書かない。
観点は 3 件までとし、4 件以上なら PR の分割を再検討する。

### 関連

依存 PR、依存される PR、関係する Issue を一覧にする。
各項目には番号または URL だけでなく、依存方向や関係する理由を書く。
該当する項目がなければ、見出しごと置かない。

## 主張に根拠を添える

外部ドキュメントを根拠にする場合は、該当箇所へ直接届く URL と必要な短い引用を添える。
CI の失敗を根拠にする場合は、ジョブの URL と失敗を示すログを添える。
推測は推測だと明示し、確かめなかった理由を書く。
指示や仕様にない判断を補った場合は、補った箇所と根拠を明示する。

数値を主張する場合は、結果を `検証` に置き、次をすべて満たす。

- 測定器が対象を正しく測ることを既知の入力などで確認する
- 変更前後を同じマシン、負荷、データ、順序、タイミングで測る
- 比較結果を条件別の表にし、対象コミット、試行回数、中央値やばらつきを示す
- 本文の手順から結果を再現できる実行可能なコマンドを書く
- PR の採否が数値に依存する場合は、独立した 2 手段で同じ傾向を確認する
- PR 本文とコミットメッセージの数値を一致させる

数値を主張する PR では、`../design-docs-writing/SKILL.md` の検証手順に従って `verifier` に差分と PR 本文を渡す。
`verifier` が利用できない場合は数値を本文から外すか、ユーザーに判断を求める。
数値を主張しない PR では `verifier` を必須としない。

次の指摘は blocking とする。

- 比較条件、対象コミット、試行回数、ばらつき、再現コマンドのいずれかがない
- 測定器の妥当性を確認していない
- 変更前後の測定条件またはタイミングが異なる
- 採否が数値に依存するのに独立した裏取りがない
- PR 本文とコミットメッセージの数値が異なる

## Draft を作成して確認する

既定ブランチで作業せず、PR は Draft で作る。

```bash
gh pr create --draft --title '...' --body-file pr-body.md
```

Draft 作成後に差分を通して自己レビューする。
その行だけでは理由が分からない箇所、一見不要に見える箇所、既存の書き方から意図的に外した箇所には行指定コメントを検討する。
コメント案は投稿前にまとめてユーザーへ提示し、承認後に 1 回のレビュー API 呼び出しで投稿する。

push 直後は check が未登録の場合があるため、登録を待ってから監視する。

```bash
until ! gh pr checks <number> 2>&1 | grep -q 'no checks reported'; do sleep 10; done
gh pr checks <number> --watch --interval 30
```

foreground で待機できない環境では、同じ登録条件と終了条件を持つ監視機能へ置き換える。
失敗した場合は、ジョブの URL と失敗ログを確認して報告する。

ready 化はユーザーの明示指示がある場合だけ行う。
ready 化の前に次を確認する。

1. 必須の 6 章が埋まっている
2. `関連` が必要な場合だけ置かれている
3. 実施済みと未検証の状態、結果、理由が `検証` に書かれている
4. 数値の主張がある場合は測定条件と verifier の要件を満たしている
5. CI が成功している
6. 自己レビューを完了し、必要な行指定コメントを承認後に投稿している
7. 依存先がマージ済みなら base を既定ブランチへ戻している
8. スコープ外の問題を記録している

満たしていない項目があれば、残っている項目を報告する。

## 言語を合わせる

直近のコミットとマージ済み PR を読み、リポジトリの慣習に合わせる。

```bash
git log --oneline -20
gh pr list --state merged --limit 10
```

判定できない場合は、タイトルとコミットメッセージを英語、本文と行指定コメントを日本語にする。
1 つの PR 本文の中で言語を混ぜない。

## 書かないこと

- ファイルごとに差分を転記した一覧
- GitHub の差分で読めるコードの貼り付け
- 測定条件を満たさない性能や使用量の主張
- コマンド、結果、理由がないチェックボックス
- 謝辞、自己弁護、レビュー判断に不要な経緯

## 執筆後に点検する

1. 必須の 6 章が正しい順序で置かれているか
2. `関連` は必要な場合だけ末尾に置かれているか
3. `概要` は手段だけを 1 文から 3 文で説明しているか
4. `変更内容` は関心事と理由を説明し、ファイル一覧になっていないか
5. `影響範囲` は互換性、外部契約、運用に触れているか
6. `検証` の各項目に状態、手順またはコマンド、結果または未検証理由があるか
7. `レビュー観点` は具体的で 3 件以下か
8. 根拠、推測、自分で補った判断が区別されているか
9. 数値の主張がある場合は測定条件、再現性、本文との整合、verifier の要件を満たしているか
10. コミットが依存順で、各コミット単体のビルドとテストが通るか
11. 既存不具合など別目的の修正が混ざっていないか
12. 依存 PR の base と `関連` の記述が一致しているか
13. 一文一行、`§` 付きの節参照、日本語の地の文と見出しにダッシュを使わない表記を守っているか
