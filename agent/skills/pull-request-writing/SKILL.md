# Pull Request の規範

PR を出すとき、PR 本文とコミットメッセージを書くとき、変更の切り分けを決めるとき、自己レビューのコメントを付けるときは、以下の規範に従う。

この規範が守るのは 3 点である。
1 つの PR で 1 つのことだけを判断できること。
根拠が、それが必要になる場所で読めること。
数値の主張が再現できること。

文体、表記、図、情報密度は `../design-docs-writing/SKILL.md` と共有し、本書では PR に固有の点だけを定める。

## 書く場所の分担

| 置き場所 | 受け持つもの | 寿命 |
| --- | --- | --- |
| コード内コメント | なぜこの形なのかという意図。何をしているかは書かない | コードと同じ |
| 行指定のレビューコメント | その行でしか意味を持たない根拠 | PR と同じ |
| PR 本文 | 背景と目的、変更の全体構造、影響範囲、設計判断、測定結果、レビューしてほしい観点 | PR と同じ |
| コミットメッセージ | その 1 コミットをなぜこの順で入れたか | リポジトリと同じ |
| `docs/DESIGN.md` | 恒久的な設計判断、不変条件、却下した案 | プロジェクトと同じ |
| `docs/ISSUES.md` | コードを読んで確認した明確な不具合 | 修正されるまで |

境界は「その情報がどこで読まれるか」で判定する。
行を見ながらでないと意味を持たない根拠は行指定コメントに置く。
差分全体を見渡さないと意味を持たない話は PR 本文に置く。
差分が消えた後も読まれる話はコードかリポジトリの文書に置く。

同じ根拠を 2 か所に書かない。
PR 本文に書いた設計判断を行コメントで繰り返すと、レビュアーはどちらが正なのか判断できなくなる。

### 設計判断をどこに置くか

リポジトリに `docs/DESIGN.md` があるかどうかで分岐する。

**ある場合**、恒久的な設計判断の正本は `docs/DESIGN.md` に置く。
PR 本文の設計判断章には、この PR で何を決めたかを 1 項目 1 行から 3 行で書き、`DESIGN.md` の該当見出しへリンクする。
PR 本文に長い設計論を書いて `DESIGN.md` を更新しない PR は、判断の記録をマージと同時に失う。

**ない場合**、PR 本文が唯一の記録であるから、後から本文だけを読んで判断が再構成できるように自足的に書く。
リポジトリ外の議論（チャット、会議、issue のコメント）に判断を預けない。
預けるなら、その URL と、そこで決まったことの要約を本文に書く。

## 1 PR = 1 判断

**判定基準は 3 つある。**

1. 片方だけ差し戻したいことが起こりうるか。起こりうるなら分ける
2. レビューに要る観点が違うか。違うなら分ける
3. 既存不具合の修正と、新規の変更が混ざっているか。混ざっているなら必ず分ける

基準はファイルではなく目的である。
同じファイルを触る 2 つの目的は 2 つの PR であり、10 ファイルにまたがる 1 つの目的は 1 つの PR である。
「関連しているから」は分けない理由にならない。
分けない理由になるのは、片方だけをマージすると壊れることだけである。

**判定は実装に入る前に行う。**
PR の切り方とコミットの順を決めてから書き始める。
書き終えてから分けると、`rebase` と `cherry-pick` のやり直しになり、その過程で差分が変質する。

**出す直前にもう一度判定する。**
実装中に見つけた不具合をついでに直していることが多い。
それは 3 番目の基準に当たる。

**分けると判断したら、実行前に切り方を提案して確認を取る。**
提案には、何と何に分けるか、どちらを先に出すか、依存関係があるかを書く。
確認を取らずに履歴を組み替えない。

## コミットの構成

**依存順に並べる。**
後のコミットが前のコミットに依存する形にし、逆向きの依存を作らない。

**測定や検証の土台を変えるなら最初に置く。**
ベンチマーク、テストの前提、計測コード、CI の設定を変えるコミットは、それを使って評価される変更より前に来る。
土台と結果が同じコミットに入っていると、数値が変わった原因が変更なのか測り方なのか分離できない。

**メッセージには「なぜ」と実測値を書く。**
何をしたかは差分が持っているので繰り返さない。
数値を伴う変更なら、そのコミット単体での実測値を書く（§「数値の主張」）。

各コミットは、それ単体でビルドが通り、テストが通る状態にする。
通らないコミットを挟むと `bisect` が使えなくなる。

## 依存 PR の運用

依存される側を先に出す。
依存する側は `--base` を依存される側のブランチに向けて作る。

```bash
gh pr create --draft --base feat/storage-facade --title '...' --body-file pr-body.md
```

**組み替えは Draft のうちに済ませる。**
ready にした後で base を差し替えると、レビュー済みのコメントが差分から外れて宙に浮く。
組み替えが要ると分かった時点で、`gh pr ready --undo` で Draft に戻してから行う。

依存される側がマージされたら、依存する側の base を既定ブランチに向け直す。

```bash
gh pr edit 143 --base main
```

PR 本文の依存 PR 章には、依存先の PR 番号と、なぜ依存しているか（何が先に入っていないと壊れるか）を書く。
番号だけ並べても、レビュアーは先にどちらを読むべきか判断できない。

## PR 本文の章立て

**必須の 6 章**は、どれだけ小さい PR でも置く。

```
## 背景と目的
## 概要
## 影響範囲
## 検証したこと
## レビューしてほしい観点
## 非目標
```

小さい PR では 1 章 1 文でよい。
章を減らすのではなく、1 章あたりを短くして軽くする。
章が欠けると、読み手はそれが該当しないのか書き忘れなのかを区別できない。

**条件付きの 4 章**は、条件に当たるときだけ置く。
当たらないときは見出しごと置かない。
空の見出しや「なし」だけの節は、読み手に読む価値のない行を読ませる。

| 章 | 置く条件 |
| --- | --- |
| `## 依存 PR` | 他の PR がマージされていないと成立しないとき |
| `## 変更の全体構造` | 差分が複数のファイルまたは層にまたがるとき |
| `## 設計判断` | この PR で設計上の選択をしたとき |
| `## 測定結果` | 数値を主張するとき |

順序は次のとおりとする。

```
## 背景と目的
## 概要
## 依存 PR
## 影響範囲
## 変更の全体構造
## 設計判断
## 測定結果
## 検証したこと
## レビューしてほしい観点
## 非目標
```

### 背景と目的

なぜこの変更が要るのかを書く。
何が困っていたか、何が足りなかったかから始め、この PR が何を成立させるかで閉じる。

issue やチケットがあるなら URL を添える。
添えるだけで済ませず、リンクを開かなくても背景が分かる程度には本文に書く。
リンク先は消えることがあり、権限で読めない人もいる。

### 概要

何をしたかを 1 文から 3 文で書く。
背景を繰り返さず、採った手段だけを書く。

差分の要約にしない（§「書かないこと」）。
「A を B に変えた」ではなく、「A の問題を、B を挟むことで解いた」と書く。

### 影響範囲

この変更がどこまで届くかを書く。
少なくとも次の 4 つに触れる。

- 挙動が変わる利用者と、その変わり方
- 後方互換性。壊すなら、何が壊れ、移行に何が要るか
- 外から見える契約（API、設定、保存形式、CLI の引数）の変更
- 運用への影響（デプロイ手順、マイグレーション、設定の追加）

影響がないと判断したなら、「ない」ではなく、どこまで確認してそう判断したかを書く。
確認していないなら §「非目標」に回す。

### 検証したこと

何をどう確かめたかを書く。
実行したコマンドと、その結果どうなったかを書く。

自動テストで担保された範囲と、手で確かめた範囲を分ける。
手で確かめたものは、手順を再現できる形で書く。

### レビューしてほしい観点

判断の分かれ目を 3 つまで挙げる。
「全体的に問題ないか」は観点ではない。

どこで迷ったか、どこを別の形にもできたか、どこが壊れると影響が大きいかを書く。

観点が 4 つ以上になるなら、1 PR に複数の判断が入っている疑いがある。
§「1 PR = 1 判断」に戻る。

### 非目標

この PR で意図して扱わなかったことを書く。
「なし」と書かない。
少なくとも、隣接していて手を付けなかった領域が必ずある。

各項目に、扱わなかった理由を 1 行添える。
範囲外だから、別の PR で扱うから、確認していないから、のいずれかである。
最後の理由を隠さない。
確認していないものをここに書かないと、レビュー済みという事実が全体の保証として誤読される。

作業中に見つけたスコープ外の問題は、ここに残す（§「スコープ外の問題」）。

### 依存 PR

§「依存 PR の運用」に従う。

### 変更の全体構造

差分を読む順序と、変更どうしの関係を書く。
どのファイルがどう変わったかは書かない（§「書かないこと」）。

読む人が最初に開くべきファイルを 1 つ指定する。
その 1 つが決まらない PR は、たいてい構造が説明できていない。

### 設計判断

選んだ形、選ばなかった形、選んだ理由を書く。
選ばなかった形を書かない設計判断は、レビュアーが同じ検討をやり直すことになる。

`docs/DESIGN.md` があるなら、正本をそちらに書いてリンクする（§「設計判断をどこに置くか」）。

### 測定結果

§「数値の主張」に従う。

## 根拠の出所

主張には出典を添える。
出典の形は、主張の種類ごとに決まっている。

**外部ドキュメント**は、アンカー付きの URL と、そこからの引用を添える。
ページの URL だけでは、読み手はどこにその記述があるのか探すことになる。
引用は原文のまま置き、要約で置き換えない。

**CI の失敗**は、ジョブの URL と、失敗を示すログの行を添える。
「CI が落ちた」だけでは、落ちた理由が変更なのか環境なのか分からない。

```bash
gh pr checks 143                          # 各 check の状態と URL
gh run view <run-id> --log-failed | tail -n 40
```

**数値**は、条件違いを並べた表にする（§「数値の主張」）。

**推測**は、推測と分かる形にする。
確かめたことと、確かめていないことを同じ文体で書かない。
「〜のはずである」「〜と思われる」と書き、なぜ確かめなかったかを添える。

**自分の判断で補った箇所は、補ったと分かるように書く。**
仕様が曖昧だった、指示になかった、既存コードから読み取った、のいずれかを明示する。
補ったことを黙っていると、レビュアーはそれを決定済みの前提として読む。

## 数値の主張

数値を書いたときだけ、この節が発動する。
PR 本文でもコミットメッセージでも同じである。

**測定器の妥当性を先に疑う。**
測ろうとしているものを本当に測っているかを、変更前に確かめる。
既知の答えが出る入力を通す、意図的に遅くした版で差が出るかを見る、といった形で確かめ、その手順を書く。
測定器が壊れていれば、その後の測定はすべて無意味になる。

**前後は同条件・同タイミングで測る。**
同じマシン、同じ負荷、同じデータ、同じ順序で測る。
前の数値を過去の記録から持ってこない。
時間をおいて測った 2 つの数値の差は、変更の効果ではなく環境の差である可能性を排除できない。

**条件違いを並べた表にする。**

```markdown
| 条件 | 中央値 | p95 | 試行 |
| --- | --- | --- | --- |
| main (a1b2c3d) | 412 ms | 780 ms | 20 |
| 本 PR (e4f5g6h) | 189 ms | 244 ms | 20 |
```

対象コミット、試行回数、ばらつきを書く。
1 回しか測っていないなら、1 回だと書く。

**再現コマンドを書く。**
本文のコマンドをそのまま実行して表の数値に到達できることを、規範として要求する。
実行できない疑似コマンドを書かない。

**独立した 2 手段での裏取りは、PR の採否がその数値に依存するときに必須とする。**
この変更を入れるかどうかの理由が速さや使用量であるなら、別の測り方でも同じ向きの差が出ることを確かめる。
参考として添えただけの数値には要さない。
裏が取れないなら、数値を書かないという選択肢を取る。

## Draft と CI

### 出すまで

**既定ブランチで作業しない。**
作業を始める前にブランチを切る。

Draft で作る。

```bash
gh pr create --draft --title '...' --body-file pr-body.md
```

### 自己レビュー

Draft を作った直後に、自分の差分を通しで読む。
行単位の根拠が要る箇所には、行指定のコメントを付ける。

付けるのは次の 3 つに当たる箇所である。

- その行だけを見ても、なぜそうしたか分からない箇所
- 一見不要に見えるが必要な箇所
- 意図的に既存の書き方から外した箇所

**コメント案は、投稿前にまとめて提示して承認を取る。**
リポジトリに通知が飛ぶ以上、外向きの行為として扱う。

承認を得たら、レビュー API で全件を一括作成する。
1 件ずつ投稿すると、レビュアーに通知が複数回飛ぶ。

```bash
cat > review.json <<'EOF'
{
  "event": "COMMENT",
  "body": "自己レビュー",
  "comments": [
    { "path": "src/store.rs", "line": 42, "side": "RIGHT",
      "body": "ここで flush を挟むのは、後段の rename が同一ディレクトリを触るため。" },
    { "path": "src/store.rs", "start_line": 71, "line": 78, "side": "RIGHT",
      "body": "この分岐は既存の retry と重複して見えるが、対象のエラー型が異なる。" }
  ]
}
EOF
gh api repos/{owner}/{repo}/pulls/143/reviews --method POST --input review.json
```

`line` は差分に含まれる行だけを指せる。
複数行にまたがるなら `start_line` と `line` を組にする。

### CI の監視

push 直後は check がまだ登録されていない。
登録される前に監視を始めると、check が 0 件のまま成功と読み違える。

登録を待ってから監視に入る。

```bash
until ! gh pr checks 143 2>&1 | grep -q 'no checks reported'; do sleep 10; done
gh pr checks 143 --watch --interval 30
```

foreground の `sleep` が使えない環境では、待ちを Monitor に置き換え、同じ条件でループする。

失敗したら、ジョブの URL とログの行を根拠として扱う（§「根拠の出所」）。

### ready にする

**ready 化はユーザーの明示の指示があったときだけ行う。**
レビューを依頼する行為であり、判断はユーザーのものである。

エージェントは、次のチェックリストを満たしたことを報告するところまでを行う。

1. 必須の 6 章が埋まっている
2. 該当する条件付き章が置かれている
3. CI が緑である
4. 自己レビューのコメントを投稿済みである
5. 依存 PR がある場合、依存先がマージ済みで base を向け直してある
6. スコープ外の問題を記録済みである

満たしていない項目があるなら、どれが残っているかを添えて報告する。

## スコープ外の問題

見つけても直さない。
直せば §「1 PR = 1 判断」の 3 番目の基準に反する。

記録先は次のとおりとする。

`docs/ISSUES.md` があるなら、そこに 1 項目として起票し、PR 本文の非目標章から ID で指す。
起票の書き方は `../design-docs-writing/SKILL.md` に従う。

ないなら、PR 本文の非目標章に 1 行で書く。
どこで見つけたかを、行番号付きのリンクで添える。

非目標章から `ISSUES.md` の項目へリンクを張らない。
`ISSUES.md` の項目は修正とともに消えるので、リンクは必ず切れる。
ID で指しておけば、見つからないこと自体が修正済みという情報になる。

## 言語

リポジトリの慣習に合わせる。
直近のコミットと、マージ済みの PR を読んで判定する。

```bash
git log --oneline -20
gh pr list --state merged --limit 10
```

判定できないとき（コミットがほとんどない、言語が混在している）の既定は、PR タイトルとコミットメッセージが英語、PR 本文と行指定コメントが日本語とする。

1 つの PR の中で言語を混ぜない。

## 書かないこと

**差分の要約**は書かない。
何が変わったかは差分が正本であり、それを日本語に書き直したものは PR 本文ではない。

**ファイルごとの変更一覧**は書かない。
GitHub の差分表示がすでに持っている。

**コードの貼り付け**は書かない。
該当箇所は行指定コメントか、行番号付きのリンクで指す。

**未測定の性能主張**は書かない。
「速くなったはず」「メモリを減らせるはず」は、§「数値の主張」を満たしていないなら書かない。
書きたいなら測る。

**チェックボックスだけのテンプレート**は置かない。
埋めた人しか意味が分からない箱は、レビュアーの判断材料にならない。

**謝辞と自己弁護**は書かない。
「急いで書いたので」「不慣れですが」は、レビューの判断を歪めるだけである。

## 執筆後の点検

PR を作った後、次を確認する。

1. 必須の 6 章がすべて埋まっているか
2. 背景と目的が、リンク先を開かなくても分かる形で書かれているか
3. 影響範囲が、後方互換性と外から見える契約に触れているか
4. 非目標が「なし」で済まされていないか。各項目に扱わなかった理由があるか
5. レビューしてほしい観点が 3 つ以下か。4 つ以上なら PR を分けるべきでないか
6. 変更の全体構造を置いたなら、最初に開くべきファイルが 1 つ指定されているか
7. 数値を書いたなら、条件表、対象コミット、試行回数、再現コマンドがそろっているか
8. 本文の数値とコミットメッセージの数値が一致しているか
9. 再現コマンドをそのまま実行して、表の数値に到達できるか
10. 外部ドキュメントの参照にアンカーと引用があるか
11. 推測が推測と分かる形で書かれているか。自分で補った箇所が明示されているか
12. コミットが依存順か。測定や検証の土台を変えるコミットが先頭側にあるか。`git log --oneline <base>..HEAD` で確認する
13. 各コミット単体でビルドとテストが通るか
14. 既存不具合の修正が混ざっていないか
15. 差分の要約、ファイルごとの変更一覧、コードの貼り付けが本文にないか
16. 依存 PR があるなら、base が依存先を向いているか。`gh pr view 143 --json baseRefName` で確認する
17. 一文一行か。節参照が `§` 付きか。地の文と見出しにダッシュがないか
18. 数値の主張がある PR なら、§「検証用サブエージェント」の `verifier` が `pass` したか

## 検証用サブエージェント

`../design-docs-writing/SKILL.md` の §「検証用サブエージェント」に従い、必須とする範囲と blocking の一覧を次に置き換える。

**数値の主張がある PR でのみ必須**とする。
`verifier` が利用できない場合は、数値を本文から落とすか、ユーザーに判断を仰ぐ。
数値を含まない PR では要さない。

blocking とする指摘は次のとおりとする。

- 条件表に比較対象の条件が並んでいない
- 対象コミット、試行回数、ばらつきのいずれかが欠けている
- 再現コマンドがない、または本文のコマンドで表の数値に到達できない
- 測定器の妥当性を確かめた記述がない
- 前後の測定が同条件・同タイミングでない
- PR の採否が数値に依存するのに、裏取りが 1 手段しかない
- 本文の数値とコミットメッセージの数値が食い違っている

`verifier` には差分と PR 本文の両方を渡す。
本文だけを渡すと、測定条件がコードと合っているかを確かめられない。
